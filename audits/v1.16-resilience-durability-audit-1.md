# v1.16 Resilience & Data Durability Audit (1)

**Audit:** v1.16 Audit Set #3 — Resilience and Data Durability
**Date:** 2026-06-17
**Baseline:** v1.15.0 shipped (NestJS single TypeScript runtime; Go preferred packaged runtime; chi router; `app.App` container).
**Previous audits:** #1 Contract Parity — PASS; #2 Architecture & Module Boundary — PASS.
**Type:** Read-only audit + zero behaviour change. No production code, schema, router, persistence, or forwarder logic was modified.
**Verdict:** ⚠️ **PASS WITH NOTES** (no blockers; the migrations introduced no resilience regression — see non-blocking notes).

---

## 1. Executive Summary

Portier's persistence, config flows, runtime lifecycle, forwarder failure paths, and activity recording remain **safe and durable** after the v1.14 NestJS and v1.15 chi-router migrations. The migrations are behaviour-preserving here: every durability guarantee established through v1.6 (atomic config writes, snapshot-and-restore rollback on persist failure, no-false-running-state on start failure, idempotent shutdown, bounded ephemeral activity) is **intact and parity-tested across both runtimes**.

- **Persistence:** both runtimes write rules atomically (same-dir temp + fsync + atomic rename); load-missing → `[]`, load-malformed → error, rules validated on both load and save; durability is documented in code.
- **Config flows:** export is deterministic; plan never mutates; import/apply validate before mutating and reject duplicates/invalid rules before any state change; the single mutation point (`importConfig`) rolls back on persist failure; apply gating order (errors → dry-run → destructive → drift) and the `ok:false`-never-`ok:true`-on-error invariant are preserved.
- **Runtime lifecycle:** create/update/delete/reorder/import snapshot-and-restore on persist failure (parity); start failure leaves no false running state; update restarts only when a running rule's forwarding fields change; diagnose is fully read-only; group actions report coherent partial success.
- **TCP/UDP forwarders:** startup failures report and leave no running state / leaked listener; shutdown is idempotent (`stopOnce`) with a 2 s wait + registry belt-and-suspenders cleanup; connection/session tracking is cleaned up; gen-guarded UDP idle timers prevent stale-timer expiry; counters are atomic; the bidi-last multi-client limitation is documented.
- **Activity/error:** bounded (500) in-memory, thread-safe, newest-first, **ephemeral by design**; `Clear` does not touch rules; filters apply before limit; the error envelope is the documented no-leak mapping.

**No blocking findings.** Two **non-blocking** items are recorded: (1) a **fatal-autostart / corrupt-config startup lockout** — a single enabled rule that cannot bind (or a malformed `rules.json`) aborts the *entire* service including the management API, locking the operator out; this is consistent across both runtimes (not a migration regression) and **undocumented** → **v1.17 Migration & Recovery** follow-up; (2) documented service coverage gaps in `config`/`forwarders`/`activity` error paths (the v1.15 baseline). One **non-blocking observation** on `CreateRule` enabled-rule start failure. No remediation was performed (the fatal-autostart fix belongs to v1.17; nothing else needed fixing).

## 4. Persistence / Rule-Store Durability Findings

**Durable. PASS.**

| Concern | Go (`config.Store`) | TS (`ConfigStore`) | Result |
|---|---|---|---|
| Load missing file | `os.IsNotExist` → `[]`, no error | `ENOENT` → `[]` | ✅ identical |
| Load malformed | decode error / `Invalid JSON` / not-an-array → error | non-array / parse error → throws | ✅ |
| Load validates rules | each rule re-validated; invalid → error | each rule re-validated (`validateForwardRule`); invalid → error | ✅ |
| Save validates rules | re-validates each rule before write; invalid → error (no write) | (manager validates before `persist`) | ✅ |
| Atomic write | same-dir temp → write → `Sync` → `Close` → `Rename` (+ remove-and-retry on rename failure) | same-dir temp → `write` → `sync` → `close` → `rename` | ✅ parity (v1.6 Fix Slice 2) |
| Partial-write protection | previous file intact until rename; temp removed on pre-rename failure | same; temp removed in `finally` | ✅ no truncation/corruption |
| Error propagation | error returned to manager → rollback runs | error thrown to manager → rollback runs | ✅ |
| Durability documented | `config.go` (atomic intent) | `config-store.ts` JSDoc (explicit, references Go parity, documents the accepted Windows dir-fsync gap) | ✅ |

- The TS `ConfigStore` exposes a minimal `ConfigStoreFileOps` test seam to force write/sync/rename failures (not on any product path).
- **Minor observation (non-blocking):** Go `Store.Save` re-validates and *mutates the caller's slice in place* (`rules[index] = validated`) before marshalling. The manager passes `m.rules`, so the normalized values are written back to the in-memory list — benign (the validated form equals the stored form) and not a corruption risk. No action.
- **Naming (from audit #2, not a defect):** Go's rules-store persistence lives in the `config` package (no Go `persistence/` package); the TS server splits `persistence/` from `config/`. Cross-runtime naming asymmetry only.

## 5. Config Export / Import / Plan / Apply Resilience Findings

**Safe. PASS.**

- **Export** (`GET /api/config/export`): deterministic shape (`version`, `exportedAt`, `rules`), suitable as a backup/restore foundation. The live export emits one `config.exported` activity event (v1.14.1) via the narrow recorder; the pure builder stays side-effect-free.
- **Plan** (`POST /api/config/plan`): pure (`buildConfigPlan` over current + desired); **no mutation, no sockets, no activity**. Audit #1 confirmed the `now` clock seam keeps it deterministic.
- **Import** (`POST /api/config/import`): validates `version`/`mode`/each rule **and** rejects intra-set duplicate listen bindings (`ensureNoDuplicateBindings`) **before any mutation** → `{imported:0, errors}` with a `config.import.failed` event and **no persist/start/stop**. On the mutate path it snapshots `previousRules`+`previousRuntime`, mutates (replace: `StopAll`+replace+reset runtime; merge: append with id-regeneration + per-rule conflict check), then `persist()`; **persist failure restores both rules and runtime** (the TS merge path additionally stops any forwarders started during the merge before restoring). Enabled rules start only after a successful persist.
- **Apply** (`POST /api/config/apply`): gating order preserved (v1.6 Fix Slice 7): missing `desired` → 400; `plan.Summary.HasErrors` → `200 ok:false` (errors-first, zero counts); `dryRun` → `200 ok:true` (before the destructive gate); `destructive && !yes` → 400; `HasDrift` → `importConfig(replace)`; else `200 ok:true`. The plan is read-only; the **only** mutation is `importConfig`, which rolls back on persist failure → `writeManagerError` 500 with **no partial corruption**. The import-error guard keeps the invariant that apply never reports `ok:true` when the underlying import reports errors.

Special cases verified: duplicate rule IDs (merge regenerates clashing IDs; replace preserves), port/binding conflicts (rejected pre-mutation), invalid protocol/mode (rejected), missing `desired` (400), null `desired` (plan error → `ok:false`, not 400 — documented in audit #1), unsupported version (400), existing running rules during apply (replace `StopAll` first), persist failure during apply/import (rollback), drift detection (plan engine), activity emitted on import success/failure. **No status/envelope normalization performed.**

## 6. Runtime Lifecycle Resilience Findings

**Coherent. PASS.**

| Operation | Resilience behaviour | Parity |
|---|---|---|
| Create | append → persist; **rollback (pop) on persist failure**; then emit + start if enabled | ✅ |
| Update | snapshot `previous`; stop runtime only if `wasRunning && forwardingFieldsChanged`; replace → persist; **on persist failure restore + restart (best-effort)**; restart only when intended | ✅ |
| Delete | snapshot rules+runtime; stop runtime; remove → persist; **restore both on persist failure** | ✅ |
| Reorder | validate all ids exist first; snapshot; reorder → persist; **restore on failure**; metadata-only (no socket churn) | ✅ |
| Start | idempotent (running → return status); **on start failure: lastError set, no running state, `rule.error` emitted** (Go) / forwarder deleted so `getStatus` shows not-running (TS) | ✅ |
| Stop | idempotent (not-running → no-op); emit only if `wasRunning` | ✅ |
| Diagnose | **read-only** — transient bind/dial probes that release immediately; listen-bind skipped while running; no persist/lifecycle calls | ✅ |
| Group start/stop | per-rule results in rule order; **partial failure is one `failed` result, not an aborted op**; skip tokens (`already_running`/`not_running`); empty match handled by HTTP (404) | ✅ |
| Status / connections | derived from runtime truth; no false running state after errors; live registries snapshot under lock | ✅ |
| Activity | success and failure paths emit (created/updated/deleted/started/stopped/error; import success/failed) | ✅ |

- **No state mutation before validation** on the rejection paths; **no persistence before runtime validation** in a way that risks divergence (validation precedes mutation; mutation precedes persist; persist failure rolls back in-memory state). This is the v1.6 Test-D rollback parity rule, still satisfied in both runtimes after the migrations.
- **Observation (non-blocking):** `CreateRule`/`addRule` for an **enabled** rule persists the rule, then attempts `StartRule`; if the start fails (e.g. port in use), the rule **stays durably created** (enabled, not running, with `lastError`) but the call returns an error (mapped to a generic 500 / start error). State is internally consistent and the behaviour is identical across runtimes — an API-nuance, not corruption. No action.

## 7. TCP Forwarder Resilience Findings

**Robust. PASS.** (`service/sources/forwarders/tcp.go`)

- **Startup:** `net.Listen` failure → `setLastError` + return error; `running` stays false, no listener stored → **no false running state**.
- **Shutdown:** `stopOnce` (idempotent); sets `running=false`, closes listener + all tracked conns, waits for goroutines with a **2 s timeout** (records a timeout error), closes registry connections for the rule.
- **Accept loop:** an Accept error is only recorded/logged when still running (a Stop-induced error is ignored) → no spurious lastError on clean shutdown.
- **Per-connection:** `activeConnections` (atomic) inc/dec, `addConn`/`removeConn` tracking, registry open/close, connection-opened/closed events; **target dial failure** → `setLastError` + `tcp.connection.error` (CAS-guarded single emit) + return; bidirectional `io.Copy` with `countingWriter`; copy errors emit at most once via CAS; `CloseWrite` half-close.
- **Counters:** `bytesIn`/`bytesOut`/`activeConnections` are atomics; listener/conns/running/started/lastErr under mutex.
- **Known flake:** `TestTCPForwarderEmitsConnectionClosedEvent` is a documented socket-timing flake (passes in isolation; fails only under parallel `build:runtime` load) — it does not hide a regression (the close-event path is exercised deterministically by other tests).

Coverage gaps (structurally hard, documented): real send-buffer copy-timeout and post-stop socket-response races are not force-covered (would need invasive seams) — accepted per the v1.6 Coverage Slice D rule.

## 8. UDP Forwarder Resilience Findings

**Robust. PASS.** (`service/sources/forwarders/udp.go`)

- **Startup:** resolve/listen failures → `setLastError` + return; for one-way / bidi-last, target resolve/dial failure **closes the listen socket** before returning → no leaked listener, no false running state.
- **Shutdown:** `stopOnce`; captures + clears `listenConn`/`targetConn`/`lastClient`/`lastSessionID`/`sessions`; stops all session timers + closes session sockets + target + listen; **2 s wait**; **registry belt-and-suspenders** `CloseSessionsForRule` (covers Stop-timeout / one-way where goroutine defers don't fire) → **no session leak**.
- **Sessions (bidi-multi):** per-client session with idle timer; **`gen` guard** in `handleMultiClientPacket`/`expireSession` prevents a stale timer from expiring a session renewed by a later packet; dial failure → `setLastError` + return (no half-open session); `expireSession` closes the socket + registry session + emits closed.
- **Loops:** read errors return cleanly (recorded only if running); write/forward/return errors → `setLastError` + `udp.packet.error` (only when running).
- **Counters:** `packetsIn/Out`, `bytesIn/Out` atomic; packet-forwarded/returned events throttled (1/s) via CAS.
- **Documented limitation:** bidi-last with multiple concurrent clients may route a reply to the wrong client (only the most-recent client is tracked) — a documented UDP design limitation, not a regression.
- **Status / live sessions:** `ActiveUdpSessions` reported only for bidi-multi; reflects the live session map under lock.

Coverage gaps (documented): some read-loop send-error branches need a `net.Conn` injection seam not worth adding — accepted per v1.6 Coverage Slice D.

## 9. Activity / Error Durability Findings

**Sound. PASS.**

- **Store** (`activity/store.go`): bounded `MaxEvents=500`, thread-safe (mutex), newest-first prepend, oldest dropped on overflow. **Ephemeral by design** — "Resets on service restart" (activity is runtime diagnostics, not persisted; the durable CLI run history added in v1.12 is a separate, local CLI artifact).
- **List:** snapshot copy under lock, filters (ruleId/type/severity) applied **before** the limit, `limit<=0` → `DefaultLimit`, capped at `MaxEvents`.
- **Clear:** truncates events only; **does not touch rules** (parity with the TS/Go contract; `DELETE /api/activity` → 204).
- **Emission ordering:** rule-scoped events are emitted **after** the corresponding state change succeeds (e.g. `rule.created` after persist; `rule.error` on start failure) — failures emit useful diagnostics without implying a state change that didn't happen.
- **Error envelope (no-leak):** `writeManagerError` maps `ValidationError`→400, `ConflictError`→409, `NotFoundError`→404, else **generic 500 with the message only** (no stack/object); the NestJS filter uses the literal `"Internal server error."` for unknown throws. Activity event-type/severity sets are stable and guarded by `validate:contract` (17 types / 4 severities). The generic-500 path is intentionally not modelled in OpenAPI (documented in audit #1).

## 10. Crash / Restart Recovery Assumptions

**Mostly sound, with one significant non-blocking gap.**

- **Persisted rules** are loaded and re-validated on startup (`Load` / `loadAndStartEnabled`).
- **Enabled (autostart) rules** are started at boot via `StartEnabled` / the `loadAndStartEnabled` start loop.
- **Runtime-only state is correctly NOT persisted:** running state, live TCP connections, and UDP sessions are reconstructed from autostart (running) or simply absent — they are runtime truth, not durable state. ✅
- **Config import/export** is a viable backup/restore foundation (deterministic export; validating, rollback-safe import). ✅

> ### Finding R-1 (non-blocking, **v1.17 Migration & Recovery** follow-up): fatal autostart / corrupt-config startup lockout
>
> A **single enabled rule that fails to start at boot** (e.g. its listen port is already in use, or a privileged/`0.0.0.0` bind is denied) **aborts the entire service startup, including the management API** — in **both** runtimes:
> - **Go:** `StartEnabled` returns on the first failing rule → `runPortier` returns `fmt.Errorf("Failed to start enabled forwarding rules: …")` → `main` → `os.Exit(1)`. The HTTP server is created *after* `StartEnabled`, so the API never binds.
> - **TS:** `loadAndStartEnabled` calls `await this.startRule(...)` with no per-rule catch → throws → `main().catch` → `process.exit(1)`. The Nest app never `listen`s.
>
> A **malformed/invalid `rules.json`** has the same effect (`Load` error → `NewFromConfig` error → service won't start).
>
> **Impact:** the operator cannot reach the UI/CLI to *fix or disable* the offending rule, because the management API never came up — a recoverability/lockout risk. This is **existing, consistent behaviour (not a migration regression)** and is **undocumented**.
>
> **Recommended v1.17 direction:** make autostart non-fatal — start the management API and all *healthy* rules, mark a rule that fails to bind as `error` (with `lastError`) and surface it via status/activity, and treat a corrupt `rules.json` with a recovery policy (e.g. start the API with zero rules + a loud diagnostic rather than refusing to boot). This aligns with v1.17's "corrupt-file recovery policy" scope. **Not implemented in this audit.**

## 12. Docs / Durable-Rules Findings

- **Documented and accurate:** atomic-write durability (config-store JSDoc + the v1.6 Fix Slice 2 durable rule), persist-failure rollback parity (v1.6 Test-D rule), activity-taxonomy parity, the generic-500 no-leak policy, the bidi-last UDP limitation, the apply `ok:false` invariant (v1.6 Fix Slice 7), and the Go-coverage structural exceptions. `service/readme.md`/`server/readme.md` describe persistence/runtime ownership correctly.
- **Gap (docs-only, tied to R-1):** the **fatal-autostart / corrupt-config startup behaviour is not documented** anywhere (`docs/architecture.md`, `service/readme.md`, README, checklist). Operators have no statement that an unbindable enabled rule (or corrupt `rules.json`) prevents the whole service from starting.
- **Decision:** I did **not** add a "known limitation" note to product docs in this slice. The behaviour is a deliberate v1.17 target (Migration & Recovery — corrupt-file recovery policy), and documenting a limitation that v1.17 is about to change would create churn; recording it here as **Finding R-1** (a tracked v1.17 follow-up) is the cleaner action. If v1.17 is deferred, a one-line known-limitation note in `docs/architecture.md` becomes the right minimal step.

No misleading current guidance found; no historical logs touched.
