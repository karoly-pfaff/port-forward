## 1. Executive Summary

Portier's automation/policy/workflow surfaces are **deterministic, local-first, advisory-by-default, rollback-aware, and visible**, and the v1.14/v1.15 migrations introduced no regression. The implemented surfaces stay deliberately conservative ("not Kubernetes for ports"): they automate *existing* safe operations and never silently mutate durable state.

- **Groups** (runtime/API + CLI + UI): start/stop reuse the single-rule lifecycle (deterministic rule-order iteration, partial-success per-rule results with stable skip tokens, no rule-definition mutation); the response exposes `succeeded`/`skipped`/`failed` counts so failures are never hidden; TS/Go parity-tested.
- **Policy** (CLI-only, offline): `policy check/review/baseline/template` are **dry-run advisory** — they evaluate and report, never apply/enforce/mutate or contact the runtime; "block" is only an exit code (CI/operator gate).
- **Config plan/apply** (runtime/API + CLI): plan is read-only; apply gates destructive ops behind explicit `yes` confirmation and blocks on plan errors (`ok:false`), with the single mutation (`importConfig`) rollback-protected (audit #3).
- **Workflow** (CLI-only): `plan`/`runbook`/`template`/`report` are dry-run; `run` executes only read-only policy/baseline steps (never applies/imports/enforces); history is opt-in, bounded, versioned, compact.
- **Local analyzer** (CLI-only): `doctor`/`config doctor`/`explain` are local-only, read-only, stable-coded, warn-vs-block via exit code (`--strict`), never executing config actions.
- **Replay** (offline tooling): offline, read-only, deterministic (audit #5).
- **Client filters** (UI-only): group/status/search filters are **ephemeral React state** (no `localStorage` anywhere) — pure UI preference, never touching runtime state.

**Deferred (not implemented — confirmed absent in code; docs do not claim otherwise):** profiles, temporary/timed (TTL) starts, recipes, and persisted **local config snapshots/restore** (config export/import is the documented backup/restore foundation; `policy baseline` is a *findings* snapshot, not a config snapshot). Saved/persisted views are likewise not implemented.

**No blocking findings.** Three **non-blocking** notes carried/added: (A-1) the group-action response shares audit #5's O-2 nondeterministic-detail-ordering family only at the registry level — group **results** themselves are rule-ordered/deterministic (no issue); (A-2) docs could state explicitly that profiles/temporary-starts/recipes/snapshots are deferred (currently correct-by-omission); (A-3) the `policy.Warning` severity is defined but unused (all current violations are `error`) — intentional reserve, worth a one-line note. No remediation performed.

## 5. Group / Profile Semantics Findings

**Deterministic, partial-success-coherent, parity-tested. PASS.**

- **Determinism:** both runtimes iterate `m.rules` (rule order) and emit one result per matched rule — deterministic ordering.
- **Reuse, not reimplementation:** `StartGroup`/`StopGroup` call the single-rule `StartRule`/`StopRule`, so group actions emit the **same per-rule activity events** and cannot drift from single-rule behaviour or corrupt runtime state. Start ignores `enabled`/autostart (parity with single-rule start).
- **Partial success:** a per-rule failure is one `failed` result (with the error as `reason`) — never an aborted operation. Skip tokens are stable and documented: `already_running` (start), `not_running` (stop); statuses `started`/`stopped`/`skipped`/`failed`.
- **Failures not hidden:** `buildGroupActionResponse` returns `{group, action, total, succeeded, skipped, failed, results[]}`; the CLI maps `failed > 0` (or the no-match 404) to exit 1 (v1.8 Slice 5 rule). An empty match → HTTP 404 (not a silent success).
- **Parity:** TS/Go group behaviour + response shape + error behaviour are guarded by `validate:contract` (`runRuleGroupScenarios`, `runGroupActionScenarios`, `group:start` content parity — audit #1).
- **Group metadata safety:** `group` is validated (trimmed, ≤64 chars, no control chars; group-operation targets must be non-empty) and is **not** an automation-policy layer — it does not affect forwarding/duplicate-binding/lifecycle/status. It cannot become an unsafe policy input.
- **Profiles:** not implemented (no code); no ambiguous group-membership-as-profile behaviour exists.

Findings: none.

## 6. Policy / Dry-Run / Preflight Findings

**Advisory-only, deterministic, read-only. PASS.**

- **Policy (`policy check/review/baseline`):** `policy.Evaluate(rules, pol)` returns a `Report` and **never applies, enforces, mutates a file, or contacts the runtime** (no `Apply`/`Enforce`/`ImportConfig`/`store.Save`/`os.WriteFile`/`client.`/`http.` in the policy evaluator). `policy check --runtime` reads config via the existing read-only `client.ExportConfig()` only. Fully deterministic (file-order findings, sorted duplicate-binding findings — v1.10 rules).
- **Warn vs block:** explicit. Result is `failed` iff an `error`-severity finding is present → exit 1; otherwise `passed` → exit 0. "Block" is purely a CI/operator exit-code gate, never runtime enforcement. The `Warning` severity exists in the type but is **currently unused** (all violations are `error`) — an intentional reserve (note A-3).
- **Config plan/apply (preflight):** `plan` is read-only (`buildConfigPlan` — no mutation/sockets/activity, audit #3). `apply` is the one place with real "block" semantics, all explicit: plan errors → `ok:false` (blocked); `dryRun` → no mutation; `destructive>0 && !yes` → 400 (blocked until the operator confirms `yes:true`); drift → the single rollback-protected `importConfig`. Advisory warnings (LAN exposure) never block. No dry-run path mutates state.
- **Advisory codes:** stable (`LAN_EXPOSURE`/`MANAGEMENT_LAN_EXPOSURE`/`PRIVILEGED_PORT`/`COMMON_PORT`/`OUTSIDE_RECOMMENDED_RANGE`), parity-tested, surfaced via the rule response + diagnose + plan.
- **Visibility / consistency:** policy/plan decisions are returned in reports + exit codes; the CLI/API/offline interpretations share the same evaluator (no hidden CLI-vs-API divergence — policy is CLI-only; advisories are shared via `@portier/shared`/the Go advisory package, parity-tested).
- **No silent runtime change:** policy metadata never alters runtime behaviour.

Findings: none blocking (A-3 docs note).

## 8. Recipes / Workflows / Snapshots / Restore Findings

**Local, deterministic, dry-run-safe, failure-visible. PASS.**

- **Workflows** (`tools/cli/sources/workflow`): `plan`/`runbook`/`template`/`report` are dry-run and deterministic; `run` executes only the read-only step types (`policy.check`/`policy.review`/`policy.baseline.compare`) by reusing the existing policy/baseline engines — it **never** runs a shell, applies/imports config, enforces policy, schedules, probes, or mutates runtime/config/policy/baseline files (v1.11 rules, audit #3). An invalid plan prints the plan and exits 1 with no step run and no `--out` file. No workflow hides partial failure — `run` reports per-step `passed`/`failed`/`skipped` + a summary + result, and a failed/skipped step fails the run (exit 1); runtime-unreachable → exit 3.
- **Workflow reports** (`workflow report`): a packaging step over an EXISTING report; the normalized `report.json` drops each step's embedded policy report (no raw config/host/port payload), and the bundle excludes secrets/env/process/logs (v1.11 Slice 7 rule). Schema-versioned.
- **History** (`workflow history`): opt-in, bounded (100), **versioned** (`schemaVersion: 1`), compact metadata only (audit #5). No unbounded growth; failure handling visible (write failure warns without hiding the run result).
- **Snapshots/restore:** no distinct config-snapshot feature. **Config export/import is the documented backup/restore foundation** — export is deterministic; import validates + rejects duplicates/invalid before any mutation and is rollback-protected; restore semantics are explicit (replace vs merge modes; apply's destructive gating). `policy baseline` is a *findings* snapshot (accepted-state comparison), explicitly not a config snapshot. Larger snapshot/restore hardening is roadmap v1.17.
- **Silent-fallback check:** workflow/policy/replay inputs fail cleanly on malformed input (exit 2), never silently degrading; replay's tolerated-malformed-bundle-report path is documented (audit #5), not silent.

Findings: none.
