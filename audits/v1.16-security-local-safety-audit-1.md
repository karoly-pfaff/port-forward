# v1.16 Security & Local-Safety Audit (1)

**Audit:** v1.16 Audit Set #4 — Security and Local-Safety
**Date:** 2026-06-17
**Baseline:** v1.15.0 shipped (NestJS single TypeScript runtime; Go preferred packaged runtime; chi router; `app.App` container).
**Previous audits:** #1 Contract Parity — PASS; #2 Architecture & Module Boundary — PASS; #3 Resilience & Data Durability — PASS WITH NOTES.
**Type:** Read-only audit + zero behaviour change. No auth added, no bind defaults changed, no API/contract/router change.
**Verdict:** ⚠️ **PASS WITH NOTES** (no security blockers; local-first posture is sound and documented).

---

## 1. Executive Summary

Portier's security posture is **local-first, unauthenticated by intent, and consistently defended** for that model. The v1.14/v1.15 migrations introduced no security regression.

- **Local-only by default:** both runtimes bind `127.0.0.1:47831`; LAN exposure (`0.0.0.0`) is strictly opt-in (`--host`/`PORTIER_HOST`/`--url`), warned at boot in both runtimes, and surfaced as `MANAGEMENT_LAN_EXPOSURE` / `LAN_EXPOSURE` advisories. The CLI defaults to `http://127.0.0.1:47831` and only targets a non-local endpoint when explicitly configured.
- **No secrets in the data model:** `ForwardRule` carries only id/name/protocol/hosts/ports/enabled/udpMode/group — no passwords, tokens, keys, or credentials. Config export, activity payloads, and diagnostics therefore cannot leak secrets.
- **Path/filesystem safety:** static serving is traversal-safe in both runtimes (Go clean-as-absolute-then-join; TS `express.static` + fixed `index.html` fallback). The API never accepts an arbitrary file path — config import takes a JSON body, config export returns a JSON body.
- **Error no-leak:** both runtimes map Validation→400 / Conflict→409 / NotFound→404 and return the safe `{ "errors": [...] }` envelope; the unmatched-route 404 envelope is fixed text. NestJS fully redacts unexpected errors to the literal `"Internal server error."`.
- **Diagnostics/support artifacts** explicitly exclude OS env vars, process lists, logs, tokens, and filesystem scans; the AI-handoff prompts caution operators to review output (which may include rule names/hosts/ports) before sharing.
- **Activity/history/replay** are local — activity is ephemeral; CLI run-history stores compact metadata only (no raw configs/secrets); replay is offline/read-only.

**No blocking findings.** Five **non-blocking** notes: (S-1) the Go generic-500 echoes `err.Error()` while NestJS emits a fixed literal — a no-leak strictness divergence → **v1.19 RC hardening**; (S-2) `/api/runtime` and the support bundle expose local file paths (`configPath`/`staticDir`) — intentional local diagnostics, relevant only under opt-in LAN exposure; (S-3) config export lacks an explicit "reveals local network topology" caution in user docs (docs-only); (S-4) the free-form activity `details` map means the redaction policy must be revisited if auth/tokens are ever introduced; (S-5) the unauthenticated model is acceptable for local-first v1.x but becomes a **MUST-have-auth** if non-local management is ever made first-class (v2.0 consideration). No remediation performed.

## 5. Auth / Authorization Posture Findings

**Intentionally unauthenticated, local-first. PASS (with a v2.0 note).**

- The management API has **no authentication/authorization** — by design. Portier is a local single-user port-forwarding manager; the trust boundary is the local machine.
- **Documented:** README states the management UI "only binds to `127.0.0.1` by default and is not reachable from the LAN," and the "LAN Exposure Warning" section: "a LAN-visible management UI/API is high risk. Keep management on `127.0.0.1:47831` unless you deliberately need remote administration and have secured that access." The roadmap explicitly defers remote/team/auth beyond 2.0 ("Portier 2.0 remains local-first").

Answers to the prompt's posture questions:
- **Is unauthenticated local API acceptable for v1.x?** Yes — for the local-first model.
- **What makes it acceptable?** Default loopback bind; the trust boundary is the local user (who already controls the host); no secrets in the data model; LAN exposure is opt-in and loudly warned; docs steer users away from LAN/remote management.
- **What would make it unacceptable?** Shipping a default `0.0.0.0` bind, encouraging LAN/remote management without controls, or adding a first-class "remote administration" feature without authentication. Portier does none of these.
- **CLI/UI warnings present?** Yes — README LAN-exposure warning, boot warnings, and the `MANAGEMENT_LAN_EXPOSURE` advisory.

**Note S-5 (v2.0 consideration, non-blocking):** if Portier 2.0 ever makes non-local management first-class, **authentication becomes a MUST** (the unauthenticated forwarder-management API is dangerous when reachable by an attacker — see §10). Auth was **not** added in this audit (correctly out of scope).

## 6. Sensitive Config / Rule Data Findings

**No secrets stored. PASS (one docs note).**

- `ForwardRule` = `id, name, protocol, listenHost, listenPort, targetHost, targetPort, enabled, udpMode?, group?` — **no password/token/secret/credential/key fields**. (A `grep` for those terms in `domain`/`validation`/`config`/`shared` found only the group-action skip *tokens* `already_running`/`not_running` — not secrets.)
- **Config export** (`GET /api/config/export`, CLI `config export`) returns rules = listen/target hosts, ports, rule/group names = **the operator's local network topology**, with no secrets.
- **Activity payloads** carry topology (`remoteAddress`/`remotePort`/`targetHost`/`targetPort`/`bytes`) — no secrets (the rule model has none to leak).
- **Docs caution:** the AI-handoff prompts (`prompts/doctor.md`/`policy.md`/`workflow.md`) and the CLI support-bundle help note that output "may include rule names, hosts, ports, and group names … review the content before sharing it with a third-party service."

**Note S-3 (docs-only):** the **config export itself** (the most direct "whole network layout" artifact) lacks an explicit "exported config reveals your local network topology — treat as sensitive before sharing" note in the user docs / `docs/api-contract.md`. The broad README LAN-exposure section and the diagnostic-prompt cautions partially cover this, but a one-line config-export sensitivity note would close the gap. Recorded as a follow-up (see §13).

**Note S-4 (future-proofing):** the activity `Details map[string]any` (Go) / details object is free-form. It carries no secrets today (the model has none), but **the redaction policy must be revisited** if a future feature ever adds auth/tokens/credentials to rules or activity — already a documented principle (CLAUDE.md group-metadata / activity rules).

## 7. Diagnostics / Support-Output Safety Findings

**Safe, with documented exclusions. PASS.**

- **API diagnostic endpoints** (`/api/diagnose`, `/api/status`, `/api/runtime`, `/api/connections`, `/api/activity`, config plan/export) return only intended local diagnostic data; no raw internal errors or stack traces (see §8). Diagnose runs read-only probes and reports check results, not raw socket errors verbatim beyond the intended message.
- **CLI support-bundle** (`supportbundle.go`): **deliberately excludes** OS environment variables, process lists, logs, tokens, and arbitrary filesystem scans (documented in the command help, the manifest comment, and the CLAUDE.md durable rule). It **may** include rule names/hosts/ports (`config-export.json`) and the runtime's `configPath`/`staticDir` (`runtime.json`) — intentional diagnostic content. `manifest.json` is written last to mark a complete bundle; "contains no secrets, environment data, or filesystem scans."
- **CLI diagnostics export** (`diagnostics.go`): "does not include logs, environment variables, OS usernames, or raw files from disk." Includes the management base URL (default `127.0.0.1:47831`).
- **AI-handoff prompts** caution: "review the content before sharing it with a third-party service" and "the pasted content is the ONLY source of truth … may include rule names, hosts, ports, group names."

**Note S-2 (intentional, LAN-relevant):** `/api/runtime` and the support bundle expose **absolute local file paths** (`configPath`, `staticDir`). This is intentional local diagnostics; under the default loopback bind it stays on-machine. It only becomes an information-disclosure consideration under opt-in LAN exposure (already a documented "high risk" mode). No change recommended for v1.x.

## 8. Error No-Leak Findings

**Aligned on status mapping; one message-content divergence.**

| Path | Go (`writeManagerError`) | NestJS (`toApiError`) |
|---|---|---|
| Validation | 400 `{errors: [...]}` | 400 `{errors: [...]}` |
| Conflict | 409 `{errors: [message]}` | 409 `{errors: [...]}` |
| Not found | 404 `{errors: [message]}` | 404 `{errors: [...]}` |
| Unmatched route | 404 `{errors: ["API route was not found."]}` (fixed) | 404 `{errors: ["API route was not found."]}` (fixed) |
| **Unexpected/unknown** | **500 `{errors: [err.Error()]}`** (the error *message text*) | **500 `{errors: ["Internal server error."]}`** (fixed literal — "never leaking the exception or a stack trace") |

- Neither runtime returns stack traces or raw exception objects. The `{errors:[...]}` envelope and the fixed 404 text are safe.
- **Note S-1 (non-blocking → v1.19 RC hardening):** the Go generic-500 echoes `err.Error()`, which for an unexpected error (e.g. a persist failure) could include a local file path or internal message; NestJS fully redacts to a fixed literal. This is a **no-leak strictness divergence** — the Go runtime (the *preferred packaged runtime*) is less strict. Non-blocking (loopback default; not a stack trace; LAN exposure is opt-in and warned), but a defense-in-depth gap worth aligning. Recommendation: in v1.19, make the Go generic-500 emit a fixed literal (or a redacted message) for parity with NestJS. This was already recorded as a known cross-runtime nuance in audit #1; this audit elevates it to a hardening candidate. The generic-500 path remains intentionally unmodelled in OpenAPI (documented, audit #1) — confirmed unchanged.

## 9. Activity / History / Replay Safety Findings

**Local and bounded. PASS.**

- **Activity store:** in-memory, bounded (500), thread-safe, newest-first, **ephemeral** ("Resets on service restart"); `Clear` does not touch rules; payloads are topology only (no secrets). Audit #3 confirmed its durability behaviour.
- **CLI run history (v1.12):** stores **compact metadata only** — run id/time/workflow/result/summary/compact step metadata + emitted codes; the durable rule explicitly **excludes** raw configs, raw policies, full reports, file contents, logs, environment variables, process data, secrets, runtime URLs, and auth tokens. Local, opt-in (`--record-history`), bounded retention.
- **Replay tool (v1.13):** standalone, **offline, read-only**; analyzes saved artifacts only; never contacts the runtime, reads referenced files, executes anything, or uploads. Its outputs may surface hosts/ports/rule names *from the analyzed artifacts* — the prompts/docs caution before sharing.
- **No replay/shared-validation files were touched** in this audit, so replay coverage validation was not run.

## 10. Network Operation Safety Findings

**Safe under the local trust model. PASS.**

- **Validation:** listen host and target host validated; ports strictly validated (integer 1–65535); `udpMode` validated; duplicate listen bindings (`protocol+listenHost+listenPort`) rejected (bind-conflict safety).
- **Management vs forwarded ports** are distinct concepts (management = `47831` loopback; forwards = recommended `48000–48999`); advisories flag privileged (`<1024`), common, and out-of-range forward ports, plus LAN exposure.
- **Privileged ports:** starting a rule on `<1024` is advisory-flagged ("may require elevated permissions"); a failed bind surfaces as a start error (audit #3 R-1 notes the boot-time fatal-autostart follow-up for v1.17).
- **SSRF framing (attacker model):** forwarding to an arbitrary target host **is the product's purpose**, not a vulnerability — under the default loopback management bind, only the local user (who already controls the machine) can create rules. The danger is **not** the forwarding itself but **unauthenticated management API exposure**: if the management API were reachable by a LAN/remote attacker, that attacker could create rules forwarding to internal/sensitive targets (an SSRF-equivalent pivot) or reconfigure forwarding. This is precisely why LAN-exposed management is documented as "high risk," is opt-in, and is warned at boot — and why §5's S-5 (auth required if non-local management is ever first-class) matters for 2.0.

**Local attacker model:** a local user already has full control of the host, so the unauthenticated loopback API grants no additional privilege. **LAN/remote exposure** is the real threat surface and is opt-in + warned + advisory-flagged. **Unauthenticated remote management would be unsafe** because it would let an unauthenticated network peer create/modify forwarding rules and pivot to internal targets — hence it is explicitly out of scope for the local-first model.

## 15. Verdict

⚠️ **PASS WITH NOTES.**

Portier's local-first security posture is sound and consistently defended: loopback-by-default management bind, opt-in + warned + advisory-flagged LAN exposure, no secrets in the data model, traversal-safe static serving, JSON-body-only config import/export (no arbitrary file paths via the API), and no-leak error envelopes. The v1.14/v1.15 migrations introduced no security regression. There are no blockers.

**Blocking notes:** none.

**Non-blocking notes:**
1. **S-1** — Go generic-500 echoes `err.Error()` vs NestJS's fixed literal → **v1.19 RC hardening** (align/redact for parity).
2. **S-2** — `/api/runtime` + support bundle expose local file paths (intentional local diagnostics; LAN-exposure-relevant only).
3. **S-3** — config export lacks an explicit topology-sensitivity doc note (docs-only follow-up).
4. **S-4** — free-form activity `details`; revisit redaction if auth/tokens are ever added.
5. **S-5** — unauthenticated management is acceptable for local-first v1.x; **auth becomes a MUST** if non-local management is ever first-class (v2.0).
