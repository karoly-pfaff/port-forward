## 1. Executive Summary

After the v1.14 NestJS and v1.15 chi-router migrations, the codebase is **maintainable, cohesively factored, and free of god functions/files**. The largest functions are cohesive, single-responsibility, parity-mirrored domain logic — all tested. Duplication is overwhelmingly **intentional cross-runtime contract mirroring** (TS↔Go), and it is **guarded** (`validate:contract` 234/234 + per-runtime parity tests + the CLI DTO parity guard). No unguarded duplication of contract semantics was found.

- **NestJS server:** thin controllers (transport-only), services own logic, feature-local DTO/schema, `api/common` is not a dumping ground (audit #2). Largest function `importConfig` (138 lines) mirrors Go.
- **Go service:** `app.App`-only handlers; chi route modules; largest functions `BuildConfigPlan` (162), `ImportConfig` (95), `udp.listenLoop` (97), `configApply` (81) — all cohesive/tested. No `h.manager` bridge, no legacy dispatch, no migration-history comments in production (v1.15 Slice 14).
- **Shared/duplication:** the config-plan engine, forward-manager rollback, forwarders, validation, advisory, and activity taxonomy are deliberately mirrored TS↔Go and guarded; the CLI carries a third DTO copy guarded by Arch-D.
- **Client:** feature-organized; `ForwardRuleList.tsx` (601 lines, ~8 state hooks) is the largest component (cohesive but a decomposition candidate); 0 production `any` (audit #7).
- **CLI:** thin-handler command files (largest handler 104 lines, flag-parse-heavy); domain logic in per-domain packages (audit #2/#7).
- **Replay:** clean detect→analyze→render separation (largest fn 58 lines), offline/read-only.
- **Scripts:** `validate-contract.js` is large (2334 lines) but organized into 16 named scenario groups + a registry (Fix Slice 4); not monolithic.

**No blocking findings.** Non-blocking maintainability notes: **M-1** (the two large parity-mirrored functions `BuildConfigPlan`/`importConfig` are optional future extraction candidates — but any refactor must be done in both runtimes), **M-2** (`ForwardRuleList.tsx` decomposition candidate, pairs well with the L-1 lint-hardening), **M-3** (the v1.16 follow-up backlog is scattered across 7 audits — consolidated here for the synthesis slice), **M-4** (no complexity tooling exists; structured inspection used; a future complexity gate is optional, not recommended to adopt in v1.16). No remediation performed.

## 4. Methodology

No complexity tooling exists in the repo (no `gocyclo`/`eslint-complexity`/cyclomatic gate). Per the slice constraint, **no tooling was added**. Complexity was assessed by **structured inspection**:
- file size (`wc -l`) and per-function/method line counts (the largest functions per hotspot file);
- nested branching + responsibility count by reading the largest functions;
- duplication by cross-referencing TS↔Go semantics and the parity guards;
- coverage hotspots from audit #7 (low-coverage = complexity signal);
- prior-audit findings (#1–#7) as known maintainability inputs.

Thresholds used (heuristic, not enforced): a Go/TS function > ~120 lines or a React component > ~500 lines is flagged as an extraction *candidate* (not a defect); a file collecting unrelated concerns is flagged as a dumping-ground risk. Findings classified blocker / non-blocking / docs-only / follow-up. **M-4:** a future complexity gate (e.g. `gocyclo`, eslint `complexity`) is *possible* but is **not recommended for v1.16** (adds tooling + noise mid-audit-series); documented as optional.

## 5. NestJS Server Complexity Findings

**Maintainable. PASS.**

- **Thin controllers:** `forwards.controller.ts` (231 lines) is the largest controller — 9 endpoints, each a one-line `to…Dto(await service.…())` (audit #2). No controller does domain work.
- **Services own logic; largest functions are domain:** `forward-manager.ts importConfig` (138) and `updateRule` (56) are the largest — cohesive validate/replace/merge/rollback and patch/restart logic, mirroring Go (M-1). No service method mixes unrelated responsibilities.
- **DTO mapping repetition:** each feature has a `*.response.dto.ts` mapper + `*.schema.ts` class — repetition by the documented feature-local pattern (audit #2/#7), not a dumping ground; `api/common` holds only genuinely shared infra. The metadata-only `*.schema.ts` classes are coverage-excluded (logic-free), mappers stay 100% covered.
- **Config-plan/apply:** the engines (`config/config-plan.ts`) live beside the plan logic (Arch-B); the apply orchestration is in the config-plan helpers, not the controllers. No duplication between TS plan logic and the HTTP layer.
- **OpenAPI generation** (`openapi/openapi.ts`, 150 lines): understandable — `buildOpenApiConfig`/`generateOpenApiDocument`/`serializeOpenApiDocument`/`canonicalizeOpenApiDocument` are small, single-purpose, tested.
- **Defensive `v8 ignore`:** narrow + justified (socket timeouts, post-stop races, nullish-on-initialized-counter) — the 100/100/100 coverage is not hiding unmaintainable code (audit #7); no stale Express wrappers remain (v1.14 Slice 30/32).

Findings: none blocking. M-1 (importConfig size) carried.

## 6. Go Service Complexity Findings

**Maintainable. PASS.**

Largest functions (lines): `BuildConfigPlan` (162), `ImportConfig` (95), `udp.listenLoop` (97), `configApply` (81), `udp.handleMultiClientPacket` (78), `udp.Start` (53), `udp.Stop` (50), `statusForRule`/`UpdateRule` (44 each).

- **`configplan.BuildConfigPlan` (162) — the largest Go function:** the plan engine (match desired↔current, material-field diff, errors/warnings). Cohesive and tested, but the single longest function — an **optional** extraction candidate (e.g. split the match loop / error-collection), tempered by the requirement to keep it byte-for-byte parity with TS (M-1).
- **`manager.ImportConfig` (95):** validate → reject duplicates/invalid (pre-mutation) → replace/merge branch → persist+rollback → start-enabled. Cohesive; the replace-vs-merge branches are the natural extraction seam if ever refactored (M-1). Audited safe in #3.
- **`udp.listenLoop` (97):** a per-mode `switch` (one-way / bidi-last / bidi-multi) over the read loop. Cohesive packet dispatch; bidi-multi already delegates to `handleMultiClientPacket`. The one-way/bidi-last inline arms could be extracted but are short; acceptable. Concurrency is guarded (mutex + atomics + `stopOnce` + gen-guard) — audit #3/#5.
- **`api.configApply` (81):** the ordered gate sequence (missing-desired → hasErrors → dryRun → destructive → drift) — readable, ordered, tested (Fix Slice 7 invariant).
- **Repeated snapshot/rollback:** the create/update/delete/reorder/import rollback pattern repeats (snapshot → mutate → persist → restore-on-failure) but is short and per-method; extracting a generic transaction wrapper would obscure the per-method restore logic — **leave as-is** (the repetition is readable and parity-mirrored).
- **Repeated API response mapping:** centralized in `rule_response.go` (`rulesToResponses`/`toRuleResponse`) — the documented shared helper (audit #2), used by forwards routes + config import; not duplicated.
- **`diagnoseForward` lookup** (audit #2 note): iterates `ListRules`/`ListStatus` to find the rule before delegating — light orchestration; an optional `manager.GetRule/GetStatus` accessor tidy (carried, low-value).
- **Comments describe final architecture** (v1.15 Slice 14 removed migration-history comments) — verified in `api.go`/`routes.go`/`rule_response.go`.
- **`PruneExpired`** (audit #5 O-1): defined but unwired — a maintainability smell (dead-in-production method) as well as a leak; carried.

Findings: none blocking. M-1 + carried O-1/diagnoseForward.

## 8. Client / UI Maintainability Findings

**Maintainable; one decomposition candidate. PASS.**

- **Component sizes:** `ForwardRuleList.tsx` (601), `ForwardRuleForm.tsx` (483), `App.tsx` (460), `LiveConnectionsView.tsx` (404), `ActivityLogView.tsx` (366). All feature-organized under `features/<area>/`.
- **M-2 (non-blocking):** `ForwardRuleList.tsx` (601 lines, ~8 `useState` + `useMemo`/`useEffect`) is the largest and most stateful component — it owns search/status/group filters, group-action toolbar+result, per-row overflow menu, delete-confirm, and drag-reorder. Cohesive (all rule-list concerns) but a **decomposition candidate** (a filter bar, a group-action toolbar, and a row component would each be independently testable), following the v1.7 Slice 8 `SettingsView` precedent. Best paired with the L-1 lint-hardening (React Hooks rules would lint the extracted components). Not a defect; tested and working.
- **Repeated fetch/error handling:** `portierApi.ts` (191 lines) is a series of thin `fetch` wrappers with a repeated `const response = await fetch(...)` + response-handling pattern — a **minor optional DRY candidate** (a shared `request()` helper), but the current per-endpoint wrappers are readable and the repetition is shallow. Low value.
- **Form validation:** the client mirrors some shared validation (`validateForwardRule`) for UX, with the server authoritative — this is the documented convenience pattern (v1.8 rules), not deep contract duplication.
- **State management:** React `useState`/`useMemo` per feature; the one cross-panel concern (config-export `exporting`) is lifted appropriately (v1.7 Slice 8). No state sprawl across unrelated components.
- **Lint posture:** 0 production `any`; React Hooks lint **not active** (L-1, audit #7) — a maintainability gap that the lint-hardening slice closes.

Findings: M-2 (ForwardRuleList decomposition) + the portierApi DRY candidate (optional/low-value).
