# v1.16 Architecture & Module Boundary Audit (1)

**Audit:** v1.16 Audit Set #2 — Architecture and Module Boundary
**Date:** 2026-06-17
**Baseline:** v1.15.0 shipped (NestJS single TypeScript runtime; Go preferred packaged runtime; chi owns all Go API routes; `app.App` dependency container; no Go legacy dispatch).
**Previous audit:** v1.16 #1 Contract Parity — PASS (`audits/v1.16-contract-parity-audit-1.md`).
**Type:** Read-only audit + zero behaviour change. No production code, schema, router, or contract was modified.
**Verdict:** ✅ **PASS**

## 1. Executive Summary

After the v1.14 NestJS migration and the v1.15 Go chi-router migration, the module boundaries across the NestJS server, the Go service, the shared contract, the CLI, and the replay tool are **coherent, layered, and acyclic**, and the docs describe the final architecture.

- **NestJS server:** single TypeScript runtime; `index.ts` is the composition root; `app/` owns wiring; each feature is a `controller → service → reader/writer + schema/DTO` module under `api/<feature>/`; cross-cutting API infra is contained in `api/common/` (not a dumping ground); framework-free domain logic is homed in `forwarders/`/`config/`/`persistence/`/`connections/`/`runtime/`/`diagnostics/`/`activity/`. Controllers are transport-only; services own logic. No Express runtime remnants (only `NestExpressApplication` platform types from `@nestjs/platform-express`).
- **Go service:** `app.App` is the explicit dependency container (plain struct, no behavior); `api.go` is infrastructure-only; chi owns all routes via `routes.go`; per-feature `*_routes.go` own thin transport/orchestration handlers; `manager` owns lifecycle, `forwarders` owns TCP/UDP, `config` owns storage, `domain` is the leaf. **No `h.manager` bridge and no legacy dispatch remain.** Import direction is strictly downward (`api → app → manager → forwarders → {domain, connections, activity}`) with no cycles.
- **Shared:** contract types only; no runtime deps; no server/client/service imports.
- **CLI:** a pure API client (own DTO copies, no `@portier`/server/service imports); thin handlers in the top-level `commands` package; domain logic in per-domain packages; `commands` is the top layer (domain packages never import it).
- **Replay:** a standalone Go module (`portier/replay`), fully offline (no `net/http`, `os/exec`, `tools/cli`, or runtime internals); `core` is a leaf (never imports `commands`).
- **Docs/durable rules** describe NestJS as the single TS runtime, Go as the preferred packaged runtime, chi as the Go router, `app.App` as the container, and the canonical OpenAPI ownership. No stale Express/legacy wording in current guidance.

**No blocking findings.** Three **non-blocking** observations are recorded (a cross-runtime persistence-package naming asymmetry; the prompt's reference to a non-existent Go `persistence/` package; one minor diagnose-handler lookup), all classified as **follow-up / docs-only**, none fixed inside this audit.

## 4. NestJS Server Boundary Findings

**Clean.**

| Layer | Ownership | Evidence |
|---|---|---|
| Composition root | `index.ts` owns the server lifecycle (resolve options, `loadAndStartEnabled`, bind HTTP, graceful shutdown) and wires the live `AppRuntime` into `createNestApp` | Imports the domain modules (`ConfigStore`/`ForwardManager`/`ActivityStore`) directly — appropriate for the root. |
| App wiring | `app/` = `app.factory.ts` (build app), `app.module.ts` (static `AppModule` + `createLiveAppModule`), `runtime-context.ts` (`APP_RUNTIME`/`RuntimeContextModule`), `server-options.ts` | Live providers source from `APP_RUNTIME`; static `AppModule` (`APP_RUNTIME=null`) for OpenAPI/tests. |
| Feature modules | `api/<feature>/` = `controller → service → reader/writer/recorder token + schema + response DTO` | Verified `forwards` (controller is a pure transport adapter; every method delegates to a service and maps via `to*ResponseDto`) and `forwards.service.ts` (logic + shared `toForwardRuleResponse`). |
| Cross-cutting API infra | `api/common/` = `clock.reader`, `api-error-envelope(.filter)`, `api-errors`, `api-validation.pipe`, `api-error.schema` | Scoped to genuinely shared API concerns — **not** a generic dumping ground. |
| Domain (framework-free) | `forwarders/`, `config/` (export+plan engines), `persistence/` (config-store), `connections/`, `diagnostics/`, `activity/`, `runtime/` | Homed outside `api/` (HTTP). |
| Static / docs / health / test | `static/`, `openapi/`, `health/`, `testing/` separate | `testing/test-helpers.ts` is test-only and excluded from coverage; not a production dependency. |

- **Single runtime / no Express remnants:** the only "Express" occurrences in production code are `NestExpressApplication` types (`app.factory.ts`, `static-serving.ts`) from `@nestjs/platform-express` — NestJS's underlying HTTP platform, not a parallel Express runtime. ✅
- **Controllers transport-only / services own logic:** verified on the largest controller (`forwards.controller.ts`, 9 endpoints, each a one-line `to…Dto(await service.…())`). ✅
- **DTO/schema feature-local:** response DTOs (`*.response.dto.ts`), request DTOs (`*.body.dto.ts`/`*.query.dto.ts`), and OpenAPI schemas (`*.schema.ts`) live in their feature folder; only `ApiErrorResponseDto` is in `api/common/`. ✅ (Consistent with the v1.14 Slice 12/27 durable rules.)
- **Helper ownership:** `forward-rule-response.ts` (the shared advisory decoration used by both the list read and the create write) is documented and feature-local in `api/forwards/`. ✅
- **`config-export` split:** the pure builder + shared `configExportedActivityEvent` factory live in `config/config-export.ts`; the controller/service/recorder live in `api/config/` (the v1.14.1 split). ✅ no duplication.

**No controller doing domain work, no generic-`common` bloat, no stale migration wording.** Findings: none (clean).

## 5. Go Service Boundary Findings

**Clean.**

| Layer | Ownership | Evidence |
|---|---|---|
| Composition root | `main.go` builds `app.App` via `app.New` and passes it to `api.NewHandler` | small/isolated. |
| Dependency container | `app/app.go` — `App{Manager, Options, StartedAt, Version}`, plain struct, no behavior, `New` applies defaults | "Route modules read from `*App` — they never reach back into it to mutate process state." |
| HTTP infrastructure | `api/api.go` — `Handler`, `NewHandler`, `ServeHTTP` (API/static boundary via `isAPIPath`), `writeAPINotFound`; `routes.go` — `modularRoutes`/`buildAPIRouter` (chi) | `api.go` is infrastructure-only; **no `h.manager` bridge** (handlers read `h.app.Manager`). |
| Feature route modules | `api/*_routes.go` (health/runtime/ports/activity/status/connections/forwards/config) own thin transport/orchestration handlers | Verified `forwards_routes.go`: decode → `h.app.Manager.X` → `toRuleResponse`/`writeJSON`/`writeManagerError`; validation delegated to `validation.*`. |
| Shared HTTP plumbing | `respond.go` (`writeJSON`/`decodeRequest`/`writeManagerError`), `rule_response.go` (rule→response mappers) | `rule_response.go` documents its shared ownership (forwards routes + config import). |
| Lifecycle / runtime | `manager` (rule lifecycle), `forwarders` (TCP/UDP runtime), `connections` (live registries) | `manager → forwarders`; `forwarders` never imports `api`/`manager`. |
| Storage / contract | `config` (rules `Store` Load/Save + config parsing), `domain` (shapes/constants/id/health), `configplan`, `advisory`, `validation` | `domain` imports nothing; storage/validation import only `domain`. |
| Small/isolated | `static`, `version`, `platform`, `logger`, `options` | each minimal, no transport coupling. |

- **chi owns all routes; no legacy dispatch:** `serveLegacyAPI`/`dispatchModular`/`h.manager` are absent from production code (grep: zero non-test matches; the single `domain/id.go` flag was a regex false-positive — `h.manager` matched "bot**h** **manager**"). ✅
- **Handlers are transport/orchestration, not business engines:** all `forwards_routes.go` handlers delegate to `h.app.Manager`; `buildGroupActionResponse` is response-shaping, `diagnoseForward` looks the rule up then delegates to `diagnose.go`. ✅
- **Encoded group/id extraction is feature-owned and documented:** `ruleIDFromPath` (from `r.URL.Path`) and `groupAction` (from `r.URL.EscapedPath()` + `url.PathUnescape`) live in `forwards_routes.go`; `routes.go` documents the static-vs-`{param}` precedence and the 404-not-405 contract. ✅ (Consistent with the v1.15 Slice 10/13 durable rules.)
- **Domain stays low-level:** `domain` imports no other internal package; `forwarders`/`manager`/`config` never import `api`. ✅

**No API handler growing into business logic, no manager→API or domain→transport dependency, no forwarders→API-shape coupling, no persistence→API coupling, no cycles.** Findings: none blocking (see §11 for one naming observation).

## 10. Dependency Direction / Cycle Findings

**Acyclic in both runtimes.**

- **Go:** measured import direction (per-package grep) is strictly downward:
  `api → {app, manager, configplan, connections, advisory, config, validation, domain, options, static, activity}`;
  `app → {manager, options, version}`; `manager → {forwarders, config, connections, activity, validation, domain}`; `forwarders → {connections, activity, domain}`; `config`/`configplan`/`advisory`/`validation` → `domain`; `domain`/`connections` import nothing internal.
  `go list ./...` and `go build ./...` succeed (a cycle would fail the build). No package cycles.
- **TypeScript:** `npm run lint` and `npm run typecheck` are clean; the module layout has no cross-feature controller/service imports that violate ownership (feature modules import only `api/common/` + shared + their own domain module).
- **CLI/replay:** internal layering is one-way (`commands → domain`; replay `commands → core`), confirmed by grep (domain/core packages never import the top layer).

Findings: none.

## 14. Verdict

✅ **PASS.**

After v1.14 (NestJS) and v1.15 (Go chi router), module boundaries are coherent and layered across the NestJS server, the Go service, the shared contract, the CLI, and the replay tool. No blocking notes. Non-blocking notes:

3. `diagnoseForward` does a rule lookup via `ListRules`/`ListStatus` — an optional manager-accessor tidy.
