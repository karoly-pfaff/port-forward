# Portier v1.6 Error Handling & Exception Flow Audit 1

_Audit date: 2026-06-10. Scope: `shared/`, `server/`, `service/`, `client/`, `tools/cli/`, `tests/e2e/`, `scripts/`. Read-only analysis — no product code, tests, contracts, durable docs (other than this file), or coverage gates were changed._

This is the eighth v1.6 audit, following:

- `audits/v1.6-coverage-audit-1.md`
- `audits/v1.6-architecture-audit-1.md`
- `audits/v1.6-testing-audit-1.md`

- `audits/v1.6-design-pattern-audit-1.md`
- `audits/v1.6-duplication-audit-1.md`

It traces how errors move end-to-end through Portier — validation, API handlers, managers, persistence, forwarders, diagnostics, activity events, CLI exit codes, UI error states, contract parity, and rollback — rather than merely hunting missing `catch` blocks. Findings cite exact files/identifiers; anything not verifiable from code is marked **Unable to verify**.

Portier is a deliberately two-runtime system (TypeScript server + Go service) implementing one REST contract, with a third contract copy in the Go CLI. Error-handling parity between the two runtimes is therefore a first-class correctness concern, not an afterthought.

## Executive Summary

**Error-flow health rating: 7 / 10.**

Portier's error handling is, on the whole, deliberate and consistent. Both runtimes share one error taxonomy (`ValidationError`/`ConflictError`/`NotFoundError` → 400/409/404, everything else → 500), one error body shape (`{ "errors": [...] }`), and a tested persist-failure rollback contract in both managers (Test-D / Go `Test*PersistFailureRollsBack`). The CLI has a documented exit-code ladder (0/1/2/3/4) and a typed `ConnectionError`/`APIError` split. The client funnels every fetch through one `ensureOk` that surfaces server `errors[]` to the user. `validate:contract` already guards the headline error statuses (400/404/409) and the plan/apply error envelope across both runtimes — 167/167 at audit time.

The risks are not systemic; they are **specific divergences and guard gaps at the edges**:

- **Biggest strengths:** uniform error-class → status mapping in both runtimes; one canonical error body shape; tested rollback parity for create/update/delete/reorder/import; typed CLI connection-vs-API error split with documented exit codes; the Go manager's single `emitRuleEvent` emission path (Arch-C2).
- **Biggest risks:**
  1. **TS replace-import has no duplicate-listen-binding guard, but Go does** — a real, untested TS↔Go divergence (`forward-manager.ts` `importConfig` replace branch vs `manager.go` `ensureNoDuplicateBindings(validated)`).
  2. **Activity event-type *values* are not parity-guarded** — `validate:contract` checks `ActivityEvent` *shape* only; the duplicated 17-value cross-runtime enum can drift silently (also flagged by the duplication audit).
  3. **TS `ConfigStore.save` is non-atomic** while Go uses temp-file + fsync + atomic rename — a persistence-resilience divergence in the Node fallback runtime.
  4. **TS `ForwardManager` repeats 10 inline rule-scoped activity-emission blocks** where Go has one `emitRuleEvent` helper — drift risk between TS call sites.
- **Correctness risks:** only #1 above is a true correctness/parity divergence (silent state divergence on duplicate-binding replace-import). #3 is a durability risk on the fallback runtime under crash/disk-full. Neither is a release blocker.
- **Should any issue block further audit work?** No. All five coverage gates pass (shared 100/100/100, server 98.9/93.6/100, client 95.2/90.2/80.3, service 90.3, cli 97.7) and `validate:contract` is 167/167. The findings are improvement slices, not blockers.
- **Recommended first implementation slice:** **Error-A — add activity event-type/severity *value* parity assertions to `validate:contract`.** Cheap, tests-only, closes the highest-value silent-drift gap, and sets up Error-B/Error-C.

## Error Flow Map

```mermaid
flowchart TD
  subgraph Input
    REQ[HTTP request / CLI invocation / UI action]
  end

  REQ --> VAL{shared validation\nvalidateForwardRule / Go validation}
  VAL -- invalid --> E400[ValidationError → 400 errors:[]]
  VAL -- valid --> MGR[ForwardManager / Go manager]

  MGR --> DUP{duplicate listen binding?}
  DUP -- yes --> E409[ConflictError → 409]
  DUP -- no --> MUT[mutate in-memory map/slice]

  MUT --> PERSIST[(persist → rules.json)]
  PERSIST -- save fails --> RB[rollback in-memory + best-effort restart\n.catch / _ = StartRule]
  RB --> E500[unknown Error → 500 errors:[msg]]
  PERSIST -- ok --> ACT[emit activity event\nrule.created/updated/... or rule.error]

  MGR -. not found .-> E404[NotFoundError → 404]

  subgraph Forwarder
    START[startRule → TcpForwarder/UdpForwarder.start]
    START -- bind EADDRINUSE --> FERR[delete forwarder + rule.error event] --> E500
    START -- ok --> RUN[running; socket callbacks]
    RUN -. udp send err .-> UDPERR[status.lastError + udp.packet.error event\nbest-effort, not propagated]
  end
  MUT --> START

  subgraph Surfaces
    E400 & E404 & E409 & E500 --> APIBODY[errors:[] JSON body]
    APIBODY --> CLI[CLI: APIError → exit 1\nConnectionError → exit 3]
    APIBODY --> UI[client ensureOk → throw Error msg\n→ role=alert banner]
    ACT --> ALOG[GET /api/activity → Activity Log view]
  end

  subgraph Diagnostics
    DIAG[diagnoseRule] --> CHECKS[per-check pass/warn/fail/skip\nbind/DNS/connect — OS-specific text]
    CHECKS --> SUMM[summary aggregation] --> APIBODY
  end
```

## Critical Flow Traces

### A. Invalid create/update rule input
- **Origin:** `shared` `validateForwardRule` (TS) / `validation.ValidateForwardRuleInput` (Go).
- **Catch point:** `ForwardManager.addRule`/`updateRule` throw `ValidationError` (`forward-manager.ts:86,124,135`); Go `CreateRule`/`UpdateRule` return `ValidationError` (`manager.go:158,190`).
- **Transformation:** Express error middleware → 400 `{errors:[]}` (`api.ts:351-354`); Go `writeManagerError` `errors.As(ValidationError)` → 400 (`api.go:702-705`).
- **Visible output:** API `errors[]`; CLI `saveForwardRule` path is UI-only (no CLI create), UI `ensureOk` → field/banner error.
- **State after failure:** none mutated; validation precedes `persist`.
- **Test coverage:** `validate:contract` "POST /api/forwards (invalid) → 400 with errors[]"; unit tests both runtimes. **Parity-guarded.** ✔

### B. Persist failure rollback (create/update/delete/reorder/import)
- **Origin:** `store.save` rejects/returns error.
- **Catch point:** each mutator wraps `persist()` in try/catch (TS) or `if err := m.persist()` (Go) and restores the prior snapshot.
- **Transformation:** re-throw → 500 `{errors:[msg]}`.
- **Visible output:** API/CLI/UI error; **no activity event is emitted** (emission follows successful persist) — correct, avoids logging a success that did not happen.
- **State after failure:** in-memory map/slice restored to the pre-mutation snapshot; a forwarder stopped for a forwarding-field update is best-effort restarted. **Parity:** Test-D (TS) ↔ `Test*PersistFailureRollsBack` (Go).
- **Gap:** TS file write is non-atomic (Finding: Persistence resilience) — a *partial* on-disk write is possible even though the in-memory state is consistent.

### C. Forwarder start / bind failure (EADDRINUSE)
- **Origin:** `forwarder.start()` rejects on bind error.
- **Catch point:** `startRule` deletes the just-added forwarder and emits `rule.error` (severity `error`) before re-throwing (`forward-manager.ts:238-250`; `manager.go:395-402,415-422`).
- **Transformation:** re-throw → 500 `{errors:[msg]}` (start is not a typed error → catch-all).
- **Visible output:** API/CLI 500/exit 1; `rule.error` activity event with `failed to start: <msg>`; UI banner.
- **State after failure:** rule remains configured but stopped; runtime state cleared (`lastError` retained in Go `runtimeState`).
- **Test coverage:** unit tests both runtimes; **EADDRINUSE residual flake** on un-migrated helpers (Test-A). Not parity-guarded by `validate:contract` (a live bind race would be non-deterministic). ✔ with caveat.

### D. Config apply failure
- **Plan validation errors:** `buildConfigPlan` sets `summary.hasErrors`; apply returns **200** `ok:false` (no mutation). Guarded: `validate:contract` "invalid desired → 200 ok:false with plan.summary.hasErrors". ✔
- **Destructive without `yes`:** apply returns **400** `{errors:["Apply requires yes: true ..."]}` (`api.ts:250-253`, `api.go:650-655`). **Not in `validate:contract`** — unit-tested per runtime only (gap → Error-C).
- **Dry-run:** `ok:true dryRun:true`, no mutation — guarded + state-verified in `validate:contract`. ✔
- **Import failure during apply:** `manager.importConfig("replace")` result is **discarded** (Finding: Apply silent failure). If import rejects, apply still reports `ok:true`.
- **CLI exit code:** `applyExitCode` → 1 when `!resp.Ok`; `exitWithError` → 3 on connection failure, 2 on local file/validation. ✔
- **Parity:** plan/apply envelope parity strong; **destructive-400 and import-422 are the unguarded apply edges.**

### E. Diagnose failure path
- **Bind failure:** `tryTcpBind`/`tryUdpBind` (TS) / `tryTCPBind`/`tryUDPBind` (Go) → `status:"fail"` with OS-specific message. 2s timeout branches exist in TS (`diagnose.ts:228,251`) but not Go (Go relies on immediate `net.Listen` result) — **runtime divergence in *how* bind failure is detected**, though both yield `fail`.
- **DNS failure:** `dns.lookup` reject (TS) / `net.LookupHost` err-or-empty (Go) → `target-host` `fail`; `target-connect` → `skip`. Message text differs (Finding: Diagnose message drift).
- **Target refused/timeout:** `tryTcpConnect` → `fail`; UDP `target-connect` always `skip`.
- **Aggregation:** `buildSummary` — any `fail` → summary `fail`; else any `warn` → `warn`; else `pass`. Identical logic both runtimes.
- **Visible output:** API 200 `checks[]`+`summary`; CLI `diagnose` renders; UI diagnostics panel.
- **State:** read-only — never mutates rules or sockets.
- **Coverage:** `validate:contract` asserts check IDs, statuses, shape; **message text intentionally unguarded.** ✔

### F. Live connections / offline UI failure
- **Server error:** `/api/connections` builds summaries; no error path beyond catch-all 500.
- **Client fetch failure:** `fetchLiveConnections` → `ensureOk` throws → view renders `role="alert"` banner; app stays usable.
- **Coverage:** Test-E added an **API-failure error-banner E2E** (`page.route` aborts `/api/connections` → `role="alert"`) plus a populated-table E2E. Documented in `docs/e2e-coverage.md`. ✔

### G. Static / client serving failure
- **Missing assets / no static dir:** TS `hasStaticClient` gate (`api.ts:344,372`) — static + SPA fallback only registered when `index.html` exists; otherwise API-only. Go `static.HasClient`/`ServeClient` (`static.go`) with `http.NotFound` fallback (`api.go:75-80`). Covered by Go `static_test.go` (asset vs SPA fallback, `HasClient`).
- **Startup/static-dir issues:** non-fatal — server still serves the API. No mutation/error leak.

### Contract validation / script failure
- `validate:contract` spawns both runtimes; `startServer` retries child bind on a fresh port and `waitForReady` bails on child exit (Test-A). `compareParity` diffs normalized advisory/plan payloads field-by-field. 167/167 at audit time. Hardening opportunity: guarantee child-process kill on every exit path (Error-F).

## Error Message / Status / Exit Code Consistency

**HTTP statuses (both runtimes identical):** 400 invalid input / 404 missing rule-or-route / 409 duplicate binding / 422 import-rejected (valid structure, invalid/conflicting rules) / 500 persistence-or-runtime. Verified parity for 400/404/409 via `validate:contract`; 422 and the destructive-apply 400 are **unit-tested per runtime but not parity-guarded** (Error-C).

**API error body shape:** uniformly `{ "errors": string[] }`. Import-rejected additionally returns `{ errors, result }` (422). Apply plan-errors return `{ ok:false, ... , plan }` at **200** (not an HTTP error — intentional, the plan envelope carries the errors). Consistent across runtimes.

**CLI exit codes:** documented ladder — 0 success / 1 general+API error / 2 usage+local-file+validation / 3 connection failure / 4 drift-with-`--fail-on-drift`. One inconsistency: local file-read error is exit **1** in `config import`/`config validate` but exit **2** in `config plan`/`diff`/`apply` (Error-D).

**UI alerts:** single funnel `ensureOk` → `throw Error(body.errors.join(" "))` → `role="alert"` banner; status code is dropped (acceptable — the server message is the useful payload).

**Advisory/warning messages:** `@portier/shared` is canonical; Go matches; **parity-guarded by `validate:contract` content assertions + `compareParity`** (Arch-A). ✔

**Activity event messages:** rule-scoped messages are templated identically in both runtimes (`Rule "%s" created.` etc.). **Type/severity *values* are not value-parity-guarded** (Error-A).

**OS-specific text risks:** confined to **diagnose** `fail`/bind/connect messages and the catch-all 500 body. Diagnose status (not message) is the contract; the 500 body echoes raw internal text (localhost-only mitigates).

## Recovery and State Consistency

- **Create/update/delete/reorder/import rollback:** snapshot-and-restore on persist failure in both runtimes; proven by Test-D (TS) and `Test*PersistFailureRollsBack` (Go). Update additionally best-effort restarts a forwarder it stopped. ✔
- **Forwarder start-failure cleanup:** forwarder removed from the map, `rule.error` emitted, error propagated; rule stays configured-but-stopped. ✔
- **Stop idempotency:** `stopRule` is a no-op when no forwarder is registered (TS `forward-manager.ts:255`; Go `stopRuntime` deletes runtime entry when `lastError==""`). ✔
- **Partial import/apply cleanup:** replace mode stops all, swaps, and on persist failure restores `previousRules`/`previousRuntime`; merge stops any forwarders it started before restoring. ✔ (caveat: replace-import duplicate-binding divergence, Finding #1).
- **Socket cleanup:** UDP `stop` closes all session sockets, listen+target sockets, and clears registry sessions; TCP forwarder cleans up on close/error.
- **Temp file cleanup:** Go `config.Save` `defer os.Remove(tempPath)` unless rename succeeds (`config.go:73-78`). TS has no temp file (non-atomic write — Finding #3).
- **Process cleanup in scripts:** `validate-contract.js` kills the spawned child; Error-F recommends guaranteeing it on all exit paths.
- **UI state after failed fetch:** views render a `role="alert"` banner and remain interactive; Test-E regression-guards the connections view.
