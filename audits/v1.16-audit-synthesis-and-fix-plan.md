## 1. Executive Summary

The v1.16 **Post-Migration Architecture & Reliability Audit** is complete: ten read-only audits covering contract parity, architecture/module boundaries, resilience/durability, security/local-safety, observability/replay, automation/policy/workflow, testing/coverage, complexity/maintainability, docs/UX, and release readiness. The result is **3 PASS, 7 PASS WITH NOTES, 0 FAIL, 0 release blockers**.

After the v1.14 NestJS migration and v1.15 Go chi-router migration, Portier is **structurally sound and release-ready as a hardening release**: the API contract is parity-clean (234/234), module boundaries are coherent and acyclic, persistence/rollback are durable and parity-tested, the local-first security posture is intact, observability/replay are deterministic and local-safe, automation is advisory/rollback-aware, tests/coverage are meaningful with no gate lowered, complexity is contained with no god functions, docs match the post-migration reality, and the release machinery (versions/OpenAPI flow/package layout/smoke) is consistent.

**No MUST-before-v1.16.0 item exists.** Three small remediations were already completed during the audits (S-3, RR-1, RR-2). The remaining backlog is a handful of **tiny docs-completeness SHOULDs**, several **NICE** optionals, and a clean set of **DEFER** items mapped to v1.17 (Migration & Recovery), v1.18 (Install/Service/Upgrade), and v1.19 (RC Hardening). The recommended path is **Option A — Ship-clean-docs**: apply the tiny docs SHOULDs, run the full release matrix, bump the nine version surfaces, regenerate OpenAPI, finalize the changelog, and tag v1.16.0.

## 4. Classification Method

Each finding is classed by **release impact**, not by how interesting it is:

- **MUST before v1.16.0** — blocks a safe hardening release (contract/API drift, failing gate, data loss/corruption from v1.14/v1.15, broken build/release, operator-harmful docs, packaging drift that invalidates the release). *Expected empty.*
- **SHOULD before v1.16.0** — tiny, low-risk, no-behavior fixes worth doing for a cleaner release (small docs completeness/navigation/notes).
- **NICE after v1.16.0** — useful but not worth delaying the tag (cosmetic, optional decompositions/polish, optional gate raises).
- **DEFER → v1.17 / v1.18 / v1.19** — belongs to a later milestone by theme.
- **DO-NOT-DO** — explicitly low-value or out-of-stage-scope.
- **DONE** — already remediated during the audit set.

Severity is independent of class (a high-value item can still be a DEFER if it belongs to a later milestone — e.g. R-1).

## 13. Recommended Minimal v1.16 Fix Plan

Three options, in increasing scope. **Recommended: Option A.**

### Option A — Ship-clean-docs (recommended)
Apply only the tiny, no-behavior docs SHOULDs, then release.
- D-1 (api-contract error/method conventions), D-2 (docs index navigation), A-3 (`policy.Warning` reserved note); optionally A-2 (deferred-automation note) and O-3/#2-b (one-liners).
- **Risk:** minimal — docs-only, no behavior/contract/gate change.
- **Why recommended:** closes every PASS-WITH-NOTES *docs* note for a polished hardening release while keeping the code surface untouched; all reliability items defer cleanly to their proper milestones.

### Option B — Ship-with-one-code-hardening (optional)
Option A **plus** the O-1 UDP `PruneExpired` wiring + reclaim test (and optionally R-2 error-path tests), if the maintainer wants a contained code hardening in v1.16 rather than v1.17.
- **Risk:** low but non-zero — touches the Go (and TS) UDP session registry + adds tests; requires the fuller validation set (§14).
- **Tradeoff:** pulls one resilience item forward; otherwise it sits naturally in v1.17. Only choose if you specifically want it shipped now.

### Option C — Ship audit-only (acceptable)
No further fixes; run the full release matrix, bump versions, finalize changelog, tag.
- **Risk:** acceptable — there are no blockers and S-3/RR-1/RR-2 are already done.
- **Tradeoff:** leaves D-1/D-2/A-3 as small open docs notes (carried to a later docs pass).

**Recommendation:** **Option A.** It produces a clean, fully-documented hardening release with the smallest possible change surface, and preserves the v1.17/v1.18/v1.19 boundaries.

## 17. Risks if Shipping v1.16.0 with Only SHOULD/NICE Items Deferred

- **R-1 (autostart/corrupt-config lockout) ships unfixed.** Accepted: it is **existing behavior, not a v1.14/v1.15 regression**, only triggers on an unbindable enabled rule or a corrupt `rules.json`, and is squarely in v1.17's "corrupt-file recovery" scope. Mitigation today: it is documented in the audits/roadmap; the operator can fix `rules.json`/disable the offending rule out-of-band and restart. Not a release blocker for a hardening release.
- **O-1 (one-way UDP registry growth) ships unfixed.** Accepted: slow, bounded by rule lifetime, the reported `/api/connections` view stays correct (expired entries are filtered), and it only matters for a high-cardinality one-way UDP forward on a long-lived rule. Fits v1.17/fix-slice.
- **S-1 (Go generic-500 message) ships as-is.** Accepted: not a stack-trace leak; loopback default + opt-in/warned LAN exposure mitigate; RC-hardening (v1.19) target.
- **L-1 (lint posture) ships as-is.** Accepted: production `any`=0 already; lint/typecheck are green; strict adoption is a v1.19 quality slice, not a correctness gap.
- **D-1/D-2/A-3 docs notes ship open if Option C is chosen.** Low risk (completeness, not correctness); Option A closes them.

**Net:** shipping with only SHOULD/NICE deferred carries **no correctness, contract, security, or data-integrity risk** — the deferred items are reliability/quality improvements scoped to later milestones, each with a documented rationale and (for R-1/O-1/S-1) a benign operator-visible footprint.
