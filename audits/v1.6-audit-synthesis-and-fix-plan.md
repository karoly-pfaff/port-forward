# Portier v1.6 Audit Synthesis & Fix Plan

_Synthesis date: 2026-06-10. Inputs: the ten completed v1.6 audits under `audits/`. This is a **fix-prioritization pass**, not a release checkpoint. No product code, tests, contracts, durable docs (other than this file), or coverage gates were changed. The audit reports are the source of truth; where a finding appears in several audits it is merged into one consolidated fix cluster and prioritized by risk and value, not by how many audits mention it._

## Executive Summary

**Overall v1.6 quality posture: strong and convergent.** Across ten audits the ratings cluster tightly — architecture 7, testing 8, complexity 8, SOLID 7, design-pattern 8, duplication 8, error-flow 7, resilience 7, readability/naming 8 (the coverage audit is unrated but its blocking tooling issue is resolved). Every audit reached the **same conclusion independently**: the codebase is in a safe state to refactor, all five coverage gates pass (shared 100/100/100, server 98.9/93.6/100, client 95.2/90.2/80.3, service 90.3, cli 97.7), `validate:contract` is 167/167, and **no finding is a release blocker**. The completed slices (Arch-A–D, Test-A/D/E, Coverage C/D/E) already extracted the highest-value seams and closed the most dangerous gaps (contract drift, apply duplication, TS rollback parity).

What remains is a short, well-understood list. The defining structural theme is **cross-runtime parity** — a handful of places where the Node fallback (TS) and the Go service diverge in behavior or durability, plus **bidirectional pattern asymmetry** (TS leads at the manager/store seams; Go leads inside the UDP forwarder). The audits converge so heavily that **a few fix slices each discharge four-to-five audits at once**.

**Biggest remaining risks (by category):**
- **Correctness / parity (one true item):** TS replace-import has no duplicate-listen-binding guard while Go does — a silent two-rules-one-port divergence (error-flow risk #1, resilience-B).
- **Durability / parity:** TS `ConfigStore.save` is non-atomic while Go writes atomically (temp+fsync+rename) — the only self-inflicted bricking path, confined to the Node fallback (resilience-A, error-flow #3).
- **Silent-drift guard gap:** activity event-type/severity *values* are parity-guarded by shape only (error-A, resilience-E, dup-G).
- **Test determinism:** residual Test-A EADDRINUSE flake on the api `/start` and TS udp-forwarder sites (testing residual, resilience-D, error-E).
- **Maintenance debt (no behavior risk):** the `validate-contract.js::runScenarios` god function (complexity-A/SOLID-A/pattern-A/dup-A/naming-D) and the TS↔Go pattern asymmetries (Go forwarder interface; TS UDP facade; TS `emitRuleEvent`).

**Recommended next 5 fix slices (detail in "Recommended v1.6 Fix Order"):**
1. **Fix-1 — TS replace-import duplicate-binding parity** (Error-C·1 / Resilience-B) — the one correctness/parity divergence.
2. **Fix-2 — TS `ConfigStore` atomic write parity** (Resilience-A) — closes the durability bricking path on the fallback.
3. **Fix-3 — Finish Test-A EADDRINUSE migration** (Test-A residual / Resilience-D / Error-E) — test determinism before anything else.
4. **Fix-4 — `validate-contract.js` scenario registry** (Complexity-A / SOLID-A / Pattern-A / Dup-A / Naming-D) — zero product risk, discharges five audits, and is a prerequisite for Fix-5.
5. **Fix-5 — Activity event-type/severity value parity guard** (Error-A / Resilience-E / Dup-G) — cheap, closes the silent-drift gap, best landed on top of the new registry.

**What should be deferred to v1.7:** the `SettingsView` decomposition (Complexity-E/SOLID-D/Pattern-F — biggest churn, lowest payoff, fully covered) and the optional Go `Store` interface (SOLID-G/Pattern-G — DIP polish, not a risk reducer).

**Is a release-readiness checkpoint appropriate yet?** **Not yet, and that is correct** — this is explicitly a fix-prioritization pass. The right move is to **commit the audit set, then execute Fix-1…Fix-3 (the correctness/durability/determinism trio)**, re-run the full validation suite, and *then* consider a v1.6 readiness checkpoint. Running a readiness checkpoint before the parity fixes would just re-surface them.
