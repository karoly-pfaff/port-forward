It evaluates **readability and naming** — the identifiers, file/module names, function/method names, type/struct names, test names, command names, API field names, event/advisory/diagnostic names, comments, and user-facing wording — by the standard the task sets: not aesthetics, but the names that affect **correctness, onboarding, runtime parity, API/CLI/UI consistency, future maintenance, test clarity, and the ability to safely continue v1.6 fixes**. Findings cite exact files/identifiers; anything not verifiable from code is marked **Unable to verify**.

Portier is a deliberately two-runtime system (TypeScript server = Node fallback; Go service = primary packaged runtime) implementing one REST contract, with a third contract copy in the Go CLI. Naming **parity** between the runtimes is a first-class concern: a concept named one way in TS and another in Go is a maintenance hazard even when the wire contract matches. This audit explicitly does **not** recommend broad renames, and recommends **no public-API field renames** — the wire contract is frozen by `validate:contract` and three consumers, and no naming issue found rises to a correctness risk that would justify breaking it.

## Executive Summary

**Readability / naming rating: 8 / 10.**

Portier's naming is, on the whole, disciplined, intention-revealing, and parity-aligned. The strongest surfaces are excellent: the **activity event-type taxonomy** (`rule.created`, `tcp.connection.opened`, `udp.session.closed`, `config.import.failed`) is a self-documenting dotted hierarchy that reads identically in both runtimes; **test names** describe behavior *and* outcome (`TestCreateForward_MalformedJSON_Returns400`, `TestImportMergeRegeneratesCollidingID`); **E2E helpers** reveal intent at the call site (`startTcpEchoServer`, `addRuleViaUI`, `startRuleViaUI`); and the recent v1.6 refactor names — Arch-C1 `domain.NewRuleID`, Arch-C2 `emitRuleEvent`, Test-A `startForwarderOnFreePort`/`startRuleStable`/`startTCPForwarderOnFreePort` — each say exactly what they do. The plan/apply type vocabulary (`ConfigPlanOperation`, `DesiredConfig`, `ConfigAppliedCounts`, `ConfigPlanRuleSnapshot`) is clear and mirrored across TS and Go.

What drags the score off a 9 is a small cluster of **terminology overloads and consistency frictions** that are cheap to document and risky to "fix" by renaming:

- **Biggest strengths:** the hierarchical activity event-type names (parity-aligned, guarded); behavior+outcome test names across all five components; intent-revealing helper names from the v1.6 refactors; clear, mirrored plan/apply type vocabulary; consistent UDP-mode names (`one-way`/`bidirectional-last-client`/`bidirectional-multi-client`) used identically everywhere.
- **Biggest readability/naming risks (all onboarding/maintenance, none correctness):**
  1. **The word "config" is heavily overloaded** — it names rule persistence (`ConfigStore`/`config-store.ts`/`config.go`), the plan/apply engine (`config-plan.ts`/`configplan`), the export/import DTO (`ExportedConfig`), the plan input (`DesiredConfig`), *and* the CLI `config` subcommand group. A reader cannot tell which "config" is meant without context.
  2. **`forward` vs `rule` split** — the REST noun is **forward** (`/api/forwards`, test `TestCreateForward_*`, UI nav "Forward Rules") but the dominant domain noun is **rule** (`ForwardRule`, `RuleStore`, `CreateRule`/`ListRules`, `ruleId`, CLI `list`). Both are reasonable; the inconsistency is the cost.
  3. **`runtime` / `server` / `service` / `node` / `go` layering** — "runtime" is simultaneously an umbrella term (either implementation), an API field (`runtime: "node"|"go"`), and an endpoint (`/api/runtime`); "server" means the Node fallback, "service" means the Go binary, and the API values are `node`/`go`. The friction is concrete in `validate-contract.js`, which special-cases `runtime === "TypeScript" && data.runtime === "node"`.
  4. **`diagnose` vs `diagnostics`** — per-rule **diagnose** (`/api/forwards/:id/diagnose`, CLI `diagnose`, `RuleDiagnosticsResult`) and the support-bundle **diagnostics export** (CLI `diagnostics export`, `diagnosticscmd.go`) share a root and sit in adjacent files, inviting confusion.
  5. **CLI command file naming is inconsistent** — `config.go` actually holds **URL resolution** (`ResolveURL`/`validateURL`), not config commands (those live in `configcmd.go`); and the `cmd` suffix is applied unevenly (`configcmd.go`/`diagnosticscmd.go` have it; `list.go`/`activity.go`/`diagnose.go` do not).
- **Any correctness / parity risks from naming?** **No.** Every TS↔Go name pair that matters for parity is semantically aligned (verified: `ForwardRule`↔`ForwardRule`, `emitRuleEvent`↔`emitRuleEvent`, `ImportConfig`↔`importConfig`, the 17 event-type strings, the plan/apply types, the `clientAddress`/`targetAddress` connection fields). The findings are onboarding/maintenance clarity, not behavior.
- **Should any issue block further work?** **No.** All five coverage gates pass, lint/typecheck are clean, and `validate:contract` last stood at 167/167. Every finding is a documentation or small-rename slice, not a blocker.
- **Recommended first implementation slice:** **Naming-A — a short durable glossary (`docs/glossary.md`) plus a canonical-terms note in CLAUDE.md/AGENTS.md.** It is zero-risk (docs only), discharges the three overload findings (config / runtime-server-service / diagnose-diagnostics) at once, and gives the *next* fix slices (and future audits) a shared vocabulary. The only *code* rename worth doing is the low-risk CLI file split (Naming-C), and it should follow the glossary.

## Naming Clarity Analysis

**Unclear or misleading identifiers (the short list).**

- **`tools/cli/sources/commands/config.go`** is the clearest miss: its name promises config-subcommand code, but it holds `ResolveURL`, `validateURL`, and the `DefaultHost`/`DefaultPort`/`DefaultURL` constants — connection/URL resolution. The actual `config` subcommands (`RunConfigExport`/`Import`/`Validate`/`Plan`/`Diff`/`Apply`) are in `configcmd.go`. A maintainer hunting the `config` command opens the wrong file first. Renaming to `url.go`/`connection.go` is a zero-risk internal fix (Naming-C).
- **"config" as a prefix** is overloaded across five unrelated concepts (see Findings). Each use is *locally* unambiguous (`ConfigStore` clearly persists rules; `ConfigPlanResponse` clearly is a plan), but a reader new to the codebase cannot infer from "config" alone which subsystem is meant. This is an onboarding tax, not a defect — best paid down by a glossary, not renames.
- **`runtime`** carries three jobs: the umbrella concept, the `GET /api/runtime` endpoint, and the `runtime: "node"|"go"` field. The cost surfaces in `validate-contract.js:419`, where the assertion must special-case `runtime === "TypeScript" && data.runtime === "node"` to bridge the human label ("TypeScript") and the API value ("node"). That inline bridge is the clearest evidence the layering needs a named, documented mapping.

**Strong naming examples (the codebase's baseline is high).**

- The **activity event-type taxonomy** (`rule.created`, `tcp.connection.opened`, `udp.packet.error`, `udp.session.closed`, `config.import.failed`) — hierarchical, predictable, parity-aligned. A reader can guess an unseen event name and be right.
- **Refactor-era helper names**: `domain.NewRuleID` (Arch-C1), `emitRuleEvent`/`emitActivity` (Arch-C2, Go), `startForwarderOnFreePort`/`startTCPForwarderOnFreePort`/`startRuleStable` (Test-A), `BuildApplyImportFromPlan`/`buildApplyImportFromPlan` (Arch-B). Each name states its job and its parity twin.
- **Plan/apply vocabulary**: `ConfigPlanOperation`, `ConfigPlanRuleSnapshot`, `ConfigAppliedCounts`, `DesiredConfig`, `hasDrift`, `destructive` — precise and mirrored.
- **Resolver/registry names**: `ResolveRule`, `TcpConnectionRegistry`/`UdpSessionRegistry`, `ensureNoDuplicateBindings`, `findDuplicateBinding`, `listenKey` — all intention-revealing.

**Names that became stale after refactors.** Only one true staleness: the **TS `forward-manager.ts` inline emission** never received Arch-C2's `emitRuleEvent` name, so the "rule event" concept is named in Go but anonymous in TS (Finding "Stale-after-refactor asymmetry"; identical fix to Dup-C2). Nothing else read as stale — the v1.6 slices kept names current with behavior.

**TS / Go naming alignment.** Verified aligned where parity matters: `ForwardRule`↔`ForwardRule`, `ForwardManager`↔`Manager` (method names mirror: `CreateRule`/`UpdateRule`/`DeleteRule`/`ReorderRules`/`ImportConfig`), `emitRuleEvent`↔(TS pending), `ensureNoDuplicate`/`ensureNoDuplicateBindings`↔same, `forwardingFieldsChanged`↔`ForwardingFieldsChanged`, `listenKey`↔`listenKey`, connection fields `clientAddress`/`targetAddress` identical, the 17 event-type strings byte-identical. The one *class* name difference (`ForwardManager` in TS, `Manager` in Go) is harmless — the Go package qualifier (`manager.Manager`) supplies the "forward" context.

## Naming Consistency Analysis

- **rule / forward / forwarding rule.** Inconsistent but bounded: REST = `/api/forwards`; domain/CLI/most code = `rule`; UI nav = "Forward Rules"; docs = "forwarding rule"/"rule". No correctness impact; a glossary line ("forward rule = rule; the REST path is the only place 'forward' is the noun") removes the ambiguity. **Do not** rename the path or `ForwardRule`.
- **config / desired config / export / import / plan / apply / drift.** The relationships are correct but dense: `import` has modes `merge`/`replace`; `apply` is plan-based and *uses* replace-import internally; `export`/`import` move `ExportedConfig`; `plan`/`diff` present a `ConfigPlanResponse`; `drift` = running ≠ desired. All terms are individually well-chosen; the overload of the bare word "config" is the only smell. Glossary, not rename.
- **diagnose / diagnostic.** Two features: per-rule **diagnose** (`/api/forwards/:id/diagnose`, `RuleDiagnosticsResult`, CLI `diagnose`) and the **diagnostics export** support bundle (CLI `diagnostics export`, `diagnosticscmd.go`). Same root, adjacent files — document the split and (optionally) rename `diagnosticscmd.go`→`diagnostics_export.go`.
- **advisory / warning.** Clean and worth preserving: **advisory** is the object (`PortAdvisory`, `/api/ports/advisory`); **warning** is a severity (`warning`) and the plan type `ConfigPlanWarning`. Keep them distinct — the glossary should lock this in so they don't blur.
- **activity / log / event.** Consistent: the codebase uses **activity event** and `ActivityStore`/`activity-store.ts`, not "log". The only "log" usage is `logger.ts`/`logger.go` (process logging) — a different, correct concept. No action.
- **live connections / sessions.** Deliberate and correct: TCP = **connection** (`TcpConnectionInfo`), UDP = **session** (`UdpSessionInfo`). The only blur is the nav label "Connections" vs the view title "Live Connections" (Finding) — a one-word UI consistency nit.
- **runtime / server / service.** The layered overload analysed above. Canonicalize in the glossary; the only code touch (optional) is a named mapping helper in `validate-contract.js`.
- **TCP / UDP naming.** Consistent casing discipline: lowercase `tcp`/`udp` in wire values and event types; `Tcp`/`Udp` in TS type names (`TcpConnectionInfo`); `TCP`/`UDP` in Go (`NewTCPForwarderWithRegistry`, `GetLiveTCPConnections`) per Go initialism convention. Cross-runtime the *wire* values match; the casing differs only where each language's idiom dictates. No action.
- **enabled / autostart / running / status.** `enabled` is the persisted desired-on flag; `running` is observed runtime state (`ForwardStatus`); `StartEnabled()` starts enabled rules at boot. No "autostart" identifier exists (the concept is "enabled" → started on launch). Clean; a glossary line tying enabled→running→StartEnabled would help newcomers.
- **plan / apply operation names.** `add`/`update`/`remove`/`unchanged` — consistent across the TS union and Go literals (the latter flagged by the duplication audit as bare literals, but the *values* are consistent). No naming inconsistency.
- **error / failed / failure.** Consistent: error-classes are `ValidationError`/`ConflictError`/`NotFoundError`; events use `.error`/`.failed` (`rule.error`, `config.import.failed`); CLI exits map cleanly. No "failure" vs "error" drift found.
- **validate:* scripts.** Self-consistent namespace: `validate:contract`/`validate:coverage`/`validate:config`/`validate:cli`/`validate:binary`/`validate:runtime`/`validate:scripts`/`validate:service:*`. The terminology block in CLAUDE.md already disambiguates them. The one mild overlap — `validate:config` (fixture compat) vs `config plan/apply` (the feature) both use "config" — is the same overload finding, covered by the glossary.

## Readability Analysis

**Long functions where names/comments matter.**

- **`scripts/validate-contract.js::runScenarios` (~384–1476, ~1090 lines).** The readability problem is *naming via comments*: each scenario is delimited only by a leading comment (`// GET /api/runtime — RuntimeInfo shape`) and identified at runtime by a `pass("GET /api/runtime → ...")` string prefix. There are no named scenario functions, so the "name" of a behavior is a free-text string repeated in pass/fail calls. This is the same artifact the complexity/SOLID/pattern/duplication audits flagged (Dup-A/Pattern-A/Complexity-A); from the *naming* angle, the fix (per-endpoint `run<Endpoint>Scenarios` functions) would turn ~50 comment-named scenarios into ~12 *named functions*, which is the readability win. The inline `runtime === "TypeScript" && data.runtime === "node"` bridge would also become a named helper.
- **`server/sources/forwarders/udp-forwarder.ts::start` (45–199, ~155 lines)** mixes abstraction levels — socket bind handshake, per-mode dispatch, and inline send-callback emission blocks (the 4 near-duplicate blocks from Dup-C1). Extracting `emitForwarded`/`emitReturned`/`emitSendError` (already the Dup-C1 slice) would *name* the three emission intents that are currently spelled out inline, raising readability without touching behavior.
- **`server/sources/diagnose.ts::diagnoseRule` (9–201)** reads well: it builds a `checks: DiagnosticCheck[]` array with clear local names (`commonPort`, `bindResult`, `connectResult`, `modeMsg`) and delegates to well-named helpers (`tryBind`/`tryTcpBind`/`tryUdpBind`/`tryTcpConnect`/`buildSummary`). The only nit is the id↔label disagreement inside the check objects (Finding). Good model for the rest.

## 100% Meaningful Coverage Interaction

- **Does naming make meaningful coverage easier or harder?** Easier, on balance.
