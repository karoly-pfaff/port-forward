# Portier v1.6 Coverage Audit 1

**Date:** 2026-06-09
**Auditor:** Claude (automated) + manual classification
**Branch:** main (post v1.6-pre ratchet, commit 7997603)
**Goal:** Map the path from current coverage to 100% meaningful coverage; flag architecture/testability risks.

---

## Executive Summary

Coverage across the five components after the v1.6-pre ratchet is healthy in measurable areas but has two blocking problems:

1. **Tooling risk — Windows vitest/v8 path case bug (intermittent).** Under certain conditions every TypeScript source file appears **twice** in `coverage-summary.json`: once with a lowercase-drive-letter path (`c:\...`) from Node.js file-URL resolution and once with an uppercase-drive-letter path (`C:\...`) from the vitest `include` glob. The uppercase entries all show 0% coverage. This doubles the statement denominator and cuts all TypeScript aggregate percentages roughly in half. The bug manifested during the first `validate:coverage` run of this audit session (shared: 26.5%, server: 41%, client: 42.5%); a second run in the same session produced clean results (shared: 100%, server: 89%, client: 95%) and all gates passed. The non-deterministic nature makes it **more dangerous** — intermittent failures in CI or on developer machines can mask real regressions or generate false alarms. The Go tooling (service, cli) is unaffected.

2. **Shared type-only files show 0% in V8.** `shared/sources/activity.ts`, `connections.ts`, and `plan.ts` are pure TypeScript type definitions (no executable JavaScript). V8 has nothing to cover in them; they will always read 0% under V8 coverage. These files must be excluded from the coverage `include` pattern or documented as structurally uncoverable.

After stripping ghost entries, the **real per-file coverage** for each component is summarized below. It matches the numbers measured at the end of the v1.6-pre ratchet session (service 87.7%, server ~89%, client ~95%, shared 100%, cli 93.2%) and all gates would pass on those real numbers.

**Whether 100% is realistic:** Yes for shared, server (excluding entry points), and most of the CLI. The service has several genuinely hard-to-cover areas (OS-level file errors, Windows service code, main.go) that are Category C/D and should be excluded with justification, not forced. The client has a browser entry point and several UI render branches that are only meaningful to test via E2E.

**Recommended first slice:** Fix the coverage tooling (the gate failures are blocking work), then address the highest-value gaps in service/manager and CLI/configcmd.

## Tooling Finding (Critical — Fix First)

### Windows path case normalization bug

**Root cause:** On Windows, Node.js resolves file URLs as `file:///c:/...` (lowercase drive letter). Vitest's coverage `include` glob resolves paths using the OS API which returns `C:\...` (uppercase drive letter). The V8 coverage reporter generates two separate JSON keys for the same physical file — one from runtime execution (lowercase) and one from static include resolution (uppercase). Both are written to `coverage-summary.json`. The `total` block aggregates all keys, doubling the denominator.

**Effect:**
- Server 89% → 41% (reported)
- Client 95% → 42% (reported)
- Shared 100% → 26% (reported)

**Fix options (in order of preference):**
1. Add `resolve.alias` path normalization in vitest configs so both paths collapse to a canonical form.
2. Use `@vitest/coverage-v8` with `normalizeWindowsPath: true` if available in the installed version.
3. Post-process `coverage-summary.json` in the `validate-coverage.js` script to deduplicate keys that differ only in drive-letter case (fold uppercase to lowercase before summing).
4. Remove `include: ['sources/**/*.ts']` from coverage configs. This disables the "all files" behavior and eliminates ghost entries. Trade-off: files never loaded by any test would no longer appear in the report. For this codebase, all source files ARE loaded by some test (except main/entry points), so the trade-off is acceptable.

**Recommended action for v1.6:** Option 3 (script-level deduplication) is the lowest-risk change with no side effects on test behavior. Option 4 is also clean if uncovered-file visibility is not needed.

### Shared type-only files

`activity.ts`, `connections.ts`, and `plan.ts` in `shared/sources/` contain only TypeScript `export type` declarations and `interface` blocks. After TypeScript compilation, these produce empty JavaScript modules (`export {}`). V8 has no statements to instrument.

The vitest `include: ['sources/**/*.ts']` pattern forces them into coverage reports as 0%/34, 0%/59, 0%/89 respectively. The `total` adds their statement counts to the denominator, deflating aggregate coverage.

**Recommended action:** Add an `exclude` entry in `shared/vitest.config.ts` for `sources/activity.ts`, `sources/connections.ts`, and `sources/plan.ts`. Alternatively, add a `/* c8 ignore file */` pragma to each. These files have zero executable content and can never be covered.
