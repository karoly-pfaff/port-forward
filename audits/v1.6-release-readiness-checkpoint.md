# Portier v1.6 Release-Readiness Checkpoint

_Checkpoint date: 2026-06-11. This is a release-**readiness** checkpoint, not the release build. No release was tagged, no installers/artifacts were produced, no version was bumped, and no product behavior was changed. The working tree was left as-is (uncommitted) for the maintainer to commit._

This checkpoint follows the completed v1.6 audit phase (10 audits) and the completed synthesis fix phase (Slices 1–8). It runs the full validation matrix and determines whether Portier is ready to proceed to v1.6 release preparation.

---

## Executive Summary

**Decision: CONDITIONAL PASS.**

Every required validation passes and **no product or release-blocking defect was found**. The condition is the standard release finalization that this checkpoint deliberately does **not** perform: the **version bump 1.5.0 → 1.6.0** across the six version files + the **changelog header finalization** (`[Unreleased — v1.6-pre]` → `[1.6.0] — <date>`). These are mechanical, well-precedented (mirroring the v1.5.0 readiness step), and carry no product risk.

- **Release blockers:** none.
- **Required pre-release actions (all mechanical, no product risk):**
  1. Bump version 1.5.0 → 1.6.0 in `package.json` (root), `client/package.json`, `server/package.json`, `shared/package.json`, `shared/sources/index.ts` (`PORTIER_APP_VERSION`), and `tools/cli/sources/version/version.go`.
  2. Finalize the changelog: change `## [Unreleased — v1.6-pre] Coverage Ratchet & Quality Hardening` to `## [1.6.0] — 2026-06-11` (and rename the section to reflect the architecture/quality-hardening release scope).
  3. At the actual release build, the Go **service** version is injected via `-ldflags "-X portier/service/sources/version.Version=1.6.0"` (it defaults to `"dev"` by design — same as v1.5; not a manual edit).
  4. Commit the Slice 1–8 working tree.
- **Recommended next step:** perform the version bump + changelog finalization, commit, then run the documented release-artifact step (`npm run build:release:current`) when actually cutting the release. **Do not** generate artifacts as part of this checkpoint.

**Why CONDITIONAL PASS, not PASS:** the codebase is release-quality, but a v1.6 release cannot ship while the version constants still read 1.5.0 and the changelog header still says "Unreleased — v1.6-pre". This is the same gate the v1.3/v1.4/v1.5 readiness steps treated as the final action.
